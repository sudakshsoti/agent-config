# OMP Configuration Audit

On 2026-08-15 we went through `omp`'s settings one by one and changed eight things. This page explains each one in plain language, says what we chose not to touch, and shows how to undo any of it.

> [!info] What `omp` even is
> `omp` (Oh My Pi) is a terminal AI coding agent. It is a separate program from Claude Code. Its settings live in `omp/config.yml` in this repo. That file is **symlinked** to `~/.omp/agent/config.yml`, which means the app and the repo are the same file. When omp writes a setting, it writes into your working tree. So `git diff` shows you what omp did, and `git checkout omp/config.yml` undoes it.

> [!danger] If you only read one thing
> **omp was sending reports about itself to a stranger's server, and we stopped it.** A default setting called `dev.autoqaConsent` was `granted`. Nobody chose that. 12 reports had already been sent before we noticed. They are now blocked. Details in [[#The privacy problem]].
>
> **The biggest risk is still open.** omp auto-approves every command it wants to run, including shell commands, in every folder you open it in. We did not change that. Details in [[#Still open: omp approves its own shell commands]].

## The privacy problem

**Fixed.** omp no longer sends anything to `qa.omp.sh`.

Here is what was happening. omp has a feature where, when its own tools misbehave, the model writes a short note about what went wrong. Those notes get saved to a small database on your Mac at `~/.omp/autoqa.db`. So far so harmless.

The part nobody chose is what happened next. A setting called `dev.autoqa` is `true` by default. A second setting, `dev.autoqaConsent`, was set to `granted`. Together those meant omp POSTed each note over the internet to `https://qa.omp.sh/v1/grievances`. That is the server of the person who writes omp. It happened in the background the moment a note was saved. There was no "push" step you had to run and no prompt.

What went out, concretely:

- A **stable install UUID** from `~/.omp/install-id`. It is the same ID every time, so every report is tied back to the same machine.
- A **free-text field written by the model**, describing the failure. Those texts named internal tooling and local file paths.
- Nothing else. ==No passwords, no API keys, no file contents.==

12 reports had already been sent by the time we looked. Every row in the database was marked as pushed. That data is on someone else's server and we cannot take it back. The change stops future sends only.

The setting is now `dev.autoqaConsent: denied` in `omp/config.yml`.

> [!warning] Do not add `dev.autoqa: true`
> The denial works because `dev.autoqa` is left **unset**. If you or a tool ever writes `dev.autoqa: true` into that file, it overrides the denial and collection starts again with no prompt. The comment in `omp/config.yml` says this too, right above the setting.

Commit: `2ca5cfd`.

## Auto-generated skills

**Fixed.** omp stopped writing skills at you, and six bad ones were moved out.

A **skill** is a small markdown file that teaches an agent how to do something. omp had a feature called `autolearn` with `autoContinue: true`. That meant at the end of every session omp ran an extra, invisible turn where the model wrote itself a new skill about what it had just learned. You paid tokens for that turn without asking for it.

In three days it produced nine skills in `~/.omp/agent/managed-skills/`. We read them. Six were junk:

- One described the `ompc` / `ompo` config overlays that were deleted a commit earlier, and named models the config no longer uses.
- One hardcoded homelab SSH targets and a uid of 10000.
- One was cut off mid-sentence.
- The rest were one-offs or copies of each other.

This matters more than it sounds because these skills load into **every** omp session automatically, and that loading is not controlled by the `autolearn` switch. A wrong skill sits in the model's instructions burning context until a human deletes the file.

So `autolearn.autoContinue` is now `false`. `autolearn.enabled` stays `true`, so the model can still write a skill when it decides one is worth writing. What is off is the unprompted capture at every stop.

The six removed skills were **moved, not deleted**. See [[#How to undo any of this]] for where and how to restore them.

Commit: `2ca5cfd`.

## Fewer skills in the system prompt

**Changed.** Nine Claude-Code-only skills no longer load into omp.

The **system prompt** is the block of instructions an agent reads before every single turn. Every skill on your machine puts its name and one-line description in there. That text costs tokens on every turn, forever.

omp was finding about 44 skills across `~/.agents/skills` and `~/.claude/skills`. Nine of them configure Claude Code itself: artifacts, the Chrome extension, keybindings, `settings.json`, scheduled cloud agents. omp has no equivalent for any of it, so those nine could never be used. They were pure cost.

`skills.ignoredSkills` in `omp/config.yml` now lists them. `homelab-deploy`, `n8n-deploy`, `orient` and `peer-review` are untouched and still load.

> [!note] This is not the Codex duplication trap
> `AGENTS.md` warns about skills appearing twice in Codex. That does not apply here. omp de-duplicates by real path, so the symlinks are fine. This was only a size trim.

Commit: `21528d6`.

## The plan reviewer's instructions were impossible

**Fixed.** The `adversary` agent now checks line numbers with `grep`.

A **subagent** is a second agent the main one hires for a specific job. `adversary` is the subagent behind `/peer-review`. Its job is to attack a plan and check whether the plan's claims about the code are real. Its instructions live in `omp/agents/adversary.md`.

Those instructions told it to check the plan's `file.ts:123` style references against the real files. It only has three tools: `read`, `grep`, `glob`. And omp's `read` returns no line numbers unless the `edit` tool is also in the session, which it is not. So the check the prompt asked for could not be done the way the prompt implied.

`grep` does return line numbers. The instruction now says to verify a cited `file:line` by grepping for the symbol and comparing. `docs/two-stage-plan-review.md` claimed the same thing and was updated to match.

The alternative was turning on `readLineNumbers` globally. We dropped that, because it would add token cost to every read in every session to buy a capability that already exists.

Commit: `7c4297a`.

## Shell commands now go to real tools

**Changed.** `bashInterceptor` is on.

When the model wants to read a file it can either run `cat README.md` in a shell, or use omp's own `read` tool. The shell version dumps raw output into context, ignores `.gitignore`, and starts background processes behind a bare `&` where nothing can watch or stop them. The **bash interceptor** spots those shell commands and reroutes them to the proper tools instead: `cat` becomes `read`, `grep` becomes `grep`, `find` becomes `glob`, background jobs go under `hub`.

Eleven rules ship with omp already. Only the on switch was missing.

> [!warning] Three of the eleven rules change what a command means
> `sed -i`, `perl -i` and `awk -i inplace` get rerouted to omp's `edit` tool, which matches text fuzzily. A command written to change exactly one thing can end up changing a different one. If an edit ever lands somewhere you did not expect, look here first.
>
> We left all eleven on anyway. Removing three would mean copying all eleven rules into `omp/config.yml` and re-comparing them against upstream after every `omp update`, forever. That standing chore costs more than the risk.

Commit: `a8f4301`.

## You can now see what a turn costs

**Changed.** `display.showTokenUsage` is `true`.

This whole config exists to be careful with quota, and there was no per-turn number telling you whether any of it worked. Now each turn shows its token count. Nothing else in this audit can be judged without that number, which is why it landed before the items that need it.

Commit: `6ee3c80`.

## Retry order follows remaining quota

**Changed.** The emptiest account is now last in line.

A **fallback chain** is the list omp walks when a model call fails. If the first model errors, it tries the next one down, and so on. `omp/config.yml` has one chain per provider under `retry.fallbackChains`.

The chain for `openrouter/*` is the one the plan reviewer uses. Its first fallback was OpenCode Go, which on 2026-08-15 was at ==86% of its weekly limit== while Codex sat at 21%. So a Gemini hiccup mid-review would fall onto the emptiest account and most likely return a 429 rate-limit error instead of a review.

Codex now answers first there, and OpenCode Go is the last rung in every chain it appears in. Nothing else moved. Every rung is still a different vendor from the one above it, so the no-Anthropic-in-the-chain rule at the top of the file still holds.

Re-check with `omp usage` before ever reordering these again.

Commit: `add84b5`.

## install.sh no longer lies, and mcp.json stays out of git

**Changed.** `./install.sh` now prints a SKIP line when omp is not installed.

Steps 3e and 3f of `install.sh` are wrapped in a check for `~/.omp/agent`. On a machine without omp they did nothing and said nothing. So a check of the form `./install.sh && readlink ~/.omp/agent/config.yml` could look like it passed when no links were ever made. It now prints a visible skip warning, matching what the script already does when `claude` is missing.

We also decided **not** to track `~/.omp/agent/mcp.json` in git, and wrote the reason into the README so a future pass does not "helpfully" add it:

- omp writes that file itself, and `omp/` is symlinked, so an `omp mcp add` for a server that takes an inline API key would write a live credential straight into a tracked working tree. `settings.json` avoids this only because `sync.sh` copies it in and can strip secrets on the way. A symlink has no such step.
- Its contents do not transfer between machines anyway. Todoist points at a local credential store, and Linear shells out to `linear auth token`.

`~/.omp/agent/extensions/` stays out for a different reason: those files are written and overwritten by whatever tool installs them, so committing them would make someone else's executable code look reviewed.

Commit: `820f917`.

## What the audit itself got wrong

Two claims in the plan turned out to be false. Worth knowing, because the plan is not gospel.

**`omp stats` does not hang.** With no flags it starts a dashboard web server and stays in the foreground on purpose. It was never going to return. `omp stats -s` prints a summary in 1.8 seconds. The plan also blamed the wrong files: it pointed at `history.db` and `agent.db` in the agent directory, but stats reads `~/.omp/stats.db`. The WAL sizes it worried about were a red herring.

**`omp gc` is not dangerous.** It is dry-run by default and does nothing at all unless you pass `--apply`.

## What one plan review actually costs

`omp stats -s` shows gemini-3.7-flash at 7 requests for $0.233. That is about ==3.3 cents per `/peer-review`==. The audit had guessed 11 cents, so it is three times cheaper than feared.

Lifetime spend across every model is $78.37.

The OpenRouter promo price ends **2026-12-31**. After that the same review costs roughly 13 cents.

## Still open: omp approves its own shell commands

**Not done. This is the biggest remaining risk.**

`tools.approvalMode` is `yolo`. The three modes:

- `always-ask` prompts before anything.
- `write` auto-approves reading and writing files, prompts before running a shell command.
- `yolo` auto-approves everything, including running shell commands, driving a browser, and spawning agents.

`yolo` is omp's shipped default, so nobody picked it. There is a small hardcoded blocklist for things like `rm -rf /`, but omp's own docs say that in yolo mode a bare critical override is ignored unless you have an explicit per-tool deny rule.

It applies in every folder you open omp in. Given `~/dev` holds this repo and the homelab repo, an unattended shell command in the wrong directory can cost you hours. Changing it is one line:

```yaml
tools:
  approvalMode: write
```

## What we deliberately did not do

### `prewalk`

**Left off, on purpose, with the reason written into `omp/config.yml`.**

Prewalk switches models mid-task. The expensive model (Opus) thinks and plans; then at the first file edit, omp swaps to the cheap `smol` model to do the typing. You pay premium rates only for the thinking.

We did not make it the default because you can just try it per run: `omp --prewalk` on a real multi-file change. Watch where the model badge switches, then compare the result against the same task without it. Turning it on globally before that trial would be a guess about output quality, and per-turn token display had only just been switched on, so there was no baseline to compare against.

Prewalk and vibe mode do not stack. A director briefing a `smol` worker that then prewalks to `smol` changes nothing.

Commit: `4beb648`.

### Vibe mode and `task.isolation.mode`

**Untouched.** In vibe mode (`/vibe`) your top session becomes a director that can only read files. It cannot edit. It spawns worker sessions on cheaper models to do the actual editing, then verifies by reading what they touched. That is a change to how you work, not just a setting, so it deserves its own trial. `task.isolation.mode` stays `none`, since the per-worker filesystem clones it enables only matter under vibe mode.

### `providers.autoThinkingModel`

**Left on `online`, and now superseded.** This setting decides which small model makes the quick "how hard should I think about this" call. Online means a remote API call to Codex, which is the emptiest account here at 21%, not the constrained one. Moving it local had no clear win.

Separately, you have decided to run **Qwen3.5 4B locally through Ollama**, both for omp and for summarising articles. Ollama v0.32.13 is installed, and since v0.30 Ollama uses Apple's MLX as its engine on Apple Silicon. ==This work is not finished.== The plan is to add `omp/models.yml` defining an Ollama provider, then point the `tiny` model role at it.

> [!caution] A model that is offered but cannot run
> `omp tiny-models list` shows `qwen3-1.7b` as disabled for local inference, because onnxruntime-node cannot run that model's export. omp still offers it as a valid value for `providers.autoThinkingModel`. So one of the listed options simply does not work.

### `retry.usageReservePolicy`

**Left at `confirm`.** This decides what happens when a fallback would land on an account that is nearly out of quota. `confirm` means a blocking prompt, which in a subagent review is a hang rather than a nuisance. The other values, `auto` and `fail-closed`, are undocumented in the installed binary. Guessing wrong either silently drains the 86%-full OpenCode Go account or hard-fails reviews that would have worked. So it was recorded as a decision for you rather than guessed at.

### `omp gc --apply`

**Not run.** The dry run says it would archive 0 sessions, delete 4 unused blobs totalling 701KB, and compact a 2.7MB write-ahead log. If you want the safe part only, `omp gc --wal --apply` does the log compaction and nothing else.

### 548MB of wasted download

**Not deleted.** There is an LFM2-700M model at:

```
~/.omp/agent/cache/tiny-models/onnx-community/LFM2-700M-ONNX
```

It was fetched before you switched to Qwen3.5 and nothing uses it. Safe to delete whenever you want the disk back.

### Pricing the adversary

Partly answered by accident, since we now know a review costs 3.3 cents. Still missing: a calendar reminder for the 2026-12-31 promo expiry, and any kind of budget cap.

## How to undo any of this

Everything that touched settings is one command:

```
git checkout omp/config.yml
```

That reverts the autoqa denial, autolearn, the interceptor, token display, the fallback order, and the ignored skills list all at once. The `adversary` prompt and `install.sh` changes are separate files, so revert them with `git revert 7c4297a` and `git revert 820f917`.

To bring back the six removed auto-generated skills:

```
mv "/private/tmp/claude-501/-Users-sudakshsoti-dev-agent-config/07af758c-283f-4576-ab4c-b442d94fa7d0/scratchpad/managed-skills-removed/"* ~/.omp/agent/managed-skills/
```

> [!warning] That folder is temporary
> It is a session scratchpad. It will be cleaned up. If you think you want any of those six skills, move them somewhere permanent this week.
