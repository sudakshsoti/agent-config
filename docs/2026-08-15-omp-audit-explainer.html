What changed in omp, what was left alone, and what is still dangerous

Ten audit items. Nine changes landed, two risks are still open by choice. Every claim below has a commit behind it, and every change can be undone with one command.

Status: partly superseded on 2026-08-29. The session-titles item below is a historical record, not current state — see the callout inside it, and docs/2026-08-29-model-roles-post-codex.md ("Model Roles After Codex") for what replaced it.

Fixed Deferred on purpose Open risk

omp was posting reports about itself to a stranger's server

When omp's own tools misbehaved, the model wrote a short note about what went wrong. Those notes were saved locally, which is harmless. Then omp POSTed each one over the internet to qa.omp.sh, the server belonging to the person who writes omp. No prompt, no push step, entirely in the background.

Two settings caused it. dev.autoqa is true by default, and dev.autoqaConsent shipped as granted. Nobody chose either.

Twelve reports had already gone by the time this was found. Each carried a stable install UUID, so every report ties back to the same machine, plus free text written by the model that named internal tooling and local file paths. No passwords, no API keys, no file contents. That data is on someone else's server and cannot be recalled. The fix stops future sends only.

# omp/config.yml dev: - autoqaConsent: granted + autoqaConsent: denied # autoqa is deliberately left UNSET. # Writing `autoqa: true` here overrides the denial.

Fixed

Nine changes, all merged to main. Grouped by what they protect: your data, then your attention, then your quota.

Privacy2ca5cfd

Auto-QA reporting denied

Covered above. dev.autoqaConsent: denied, and dev.autoqa left unset rather than set to false.

Do not add dev.autoqa: true. The denial only holds while that key is absent. If you or a tool ever writes it in, collection restarts with no prompt. There is a comment in omp/config.yml saying so.
Attention2ca5cfd

omp stopped writing skills at you

A skill is a small markdown file that teaches an agent how to do something. omp's autolearn feature had autoContinue: true, which meant that at the end of every session it ran an extra, invisible turn where the model wrote itself a new skill about what it had just learnt. You paid tokens for that turn without asking for it.

In three days it produced nine skills. Six were junk: one described config overlays that had been deleted a commit earlier, one hardcoded homelab SSH targets, one was cut off mid-sentence, and the rest were duplicates of each other.

This matters more than it sounds, because those skills load into every omp session automatically and that loading is not controlled by the autolearn switch. A wrong skill sits in the model's instructions burning context until a human deletes the file.

autoContinue is now false. autolearn.enabled stays true, so the model can still write a skill when it decides one is worth writing. What is off is the unprompted capture at every stop.

Attention21528d6

Nine unusable skills removed from the system prompt

The system prompt is the block of instructions an agent reads before every single turn. Every skill on your machine puts its name and one-line description in there, costing tokens on every turn forever.

omp was loading around 44 skills. Nine of them configure Claude Code itself: artifacts, the Chrome extension, keybindings, settings.json, scheduled cloud agents. omp has no equivalent for any of it, so those nine could never be used. Pure cost. homelab-deploy, n8n-deploy, orient and peer-review are untouched.

This is not the Codex duplication trap that AGENTS.md warns about. omp de-duplicates by real path, so the symlinks are fine. This was a size trim, nothing more.
Correctness7c4297a

The plan reviewer had been given an impossible instruction

adversary is the subagent behind /peer-review. Its job is to attack a plan and check whether the plan's claims about the code are real.

Its instructions told it to verify file.ts:123 style references against the real files. It has three tools: read, grep, glob. omp's read returns no line numbers unless the edit tool is also in the session, which it is not. So the check the prompt asked for could not be done the way the prompt implied. grep does return line numbers, so the instruction now says to grep for the symbol and compare.

The alternative was turning on readLineNumbers globally. Dropped, because it would add token cost to every read in every session to buy a capability that already exists.

Correctnessa8f4301

Shell commands now route to real tools

When the model wants to read a file it can either run cat README.md in a shell, or use omp's own read tool. The shell version dumps raw output into context, ignores .gitignore, and starts background processes behind a bare & where nothing can watch or stop them. The bash interceptor spots those and reroutes them: cat to read, find to glob, background jobs under hub. Eleven rules already shipped with omp. Only the on switch was missing.

Three of the eleven rules change what a command means. sed -i, perl -i and awk -i inplace get rerouted to omp's edit tool, which matches text fuzzily. A command written to change exactly one thing can end up changing a different one. If an edit ever lands somewhere unexpected, look here first.

All eleven were left on anyway. Removing three would mean copying all eleven into omp/config.yml and re-comparing them against upstream after every omp update, forever. That standing chore costs more than the risk.
Quota6ee3c80

You can now see what a turn costs

This whole config exists to be careful with quota, and there was no per-turn number telling you whether any of it worked. Each turn now shows its token count. Nothing else in the audit can be judged without that number, which is why it landed before the items that need it.

Quotaadd84b5

Retry order now follows remaining quota

A fallback chain is the list omp walks when a model call fails. If the first model errors it tries the next one down. The chain for openrouter/* is the one the plan reviewer uses, and its first fallback was OpenCode Go, which was sitting at 86% of its weekly limit while Codex was at 21%. So a hiccup mid-review would fall onto the emptiest account and most likely return a rate-limit error instead of a review.

Codex answers first there now, and OpenCode Go is last in every chain it appears in. Every rung is still a different vendor from the one above it, so the rule at the top of the file still holds: no Anthropic selector anywhere in the chains, meaning a failed Claude call never retries on Claude.

Re-check with omp usage before ever reordering these again.

Repo820f917

install.sh no longer stays silent, and mcp.json stays out of git

Two steps of install.sh are wrapped in a check for ~/.omp/agent. On a machine without omp they did nothing and said nothing, so a run could look like it passed when no links were ever made. It now prints a visible SKIP line, matching what the script already did when claude was missing.

Separately, ~/.omp/agent/mcp.json was deliberately left untracked, with the reason written into the README so a future pass does not helpfully add it:

  • omp writes that file itself, and omp/ is symlinked, so an omp mcp add for a server that takes an inline API key would write a live credential straight into a tracked working tree. settings.json escapes this only because sync.sh copies it in and can strip secrets on the way. A symlink has no such step.
  • Its contents do not transfer between machines anyway. Todoist points at a local credential store and Linear shells out to linear auth token.

Session titles now run on your own Mac

Superseded 2026-08-29. The ollama-local provider described in this item is gone. Ollama's desktop app was removed, so nothing listens on port 11434 and no local model can serve titles any more; the Homebrew CLI (ollama 0.33.0 at /opt/homebrew/bin/ollama) is still installed but idle, a loose end for a future brew uninstall ollama. The ollama-local block in omp/models.yml is deleted, and the install.sh symlink step that installed it (step 3i) is deleted with it. tiny is now anthropic/claude-haiku-4-5:low: Haiku 4.5 is free under Claude Max 5x, it rides a connection omp already has open, and a title prompt is only about 82 tokens, so the quota cost next to one Sonnet turn is negligible — the trade only made sense while local inference was free, and it is not free any more. tiny also fires before every turn (defaultThinkingLevel: auto means it classifies each turn's difficulty first), so its latency lands on your wait time, which is why it stays on a warm Anthropic connection instead of a cheap gateway model. See docs/2026-08-29-model-roles-post-codex.md ("Model Roles After Codex") for the current state. What follows is the 2026-08-15 record of how it was built.

Every omp session gets a short name, the three to six words in the session list. Generating that name was a paid API call. It was the smallest job omp did and there was no reason to buy it. The tiny model role pointed at ollama-local/qwen3.5:0.8b, defined in a new omp/models.yml that install.sh symlinked into place.

0.8B, not the 4B originally planned. A 4B was wired first and it worked. Then the machine's actual state surfaced: a 16GB Mac already at 10.6GB of swap out of 11GB, with 13% of memory free. The 4B holds about 4GB of RAM while loaded. Spending that on three-word titles is the wrong trade on a machine already paging to disk. Backing it out took memory free from 13% to 63% and swap down to 4.9GB. The mistake worth remembering is that the 4B was recommended before anyone checked how much RAM the machine had.

omp -p never generates titles. Title generation only fires on the interactive path. Test with -p and you will conclude the feature is broken when it is fine.
omp argued with itself about thinking. For a three-word title, reasoning was pure waste, so the config told the model not to. A logging proxy in front of Ollama caught the real request: omp sent the instruction as asked, then sent preserve_thinking: true of its own alongside it. On the 4B omp's own flag won and a single title took 78 seconds. On the 0.8B it did not. The override that forced it off was recorded in omp/models.yml, now deleted along with the rest of that provider.

Three more that cost time to find. Switching thinking off needed both reasoning: false on the model and extraBody.reasoning_effort: none; either alone did nothing. A Modelfile could not turn thinking off, it had to go in the request body. And the provider needed api: openai-completions, because the similarly named openai-responses garbled output with no clear error.

It was a full custom provider rather than a tweak to omp's built-in ollama, because the built-in discovers models by asking Ollama and caches the answer. That cache went stale: after an ollama rm, omp still listed the deleted model.

That call was vindicated after the fact. As of 2026-08-29, omp models still lists two phantom entries, ollama/qwen3.5:0.8b and ollama/qwen3.5:4b-mlx, from omp's built-in ollama provider. Nothing can serve either: there is no server on port 11434 and no weights left on disk. It is the exact stale-discovery-cache behaviour the original omp/models.yml comment warned about, left as harmless history rather than something to fix.
The 0.8B sat at 1.1GB of RAM while loaded, not the 600MB expected. It unloaded after five minutes idle. Superseded 2026-08-29: Ollama's desktop app is gone, so git revert c474b30 would not put titles back on the paid API on its own — the provider it depends on no longer runs, and tiny is now anthropic/claude-haiku-4-5:low regardless. ~/.ollama no longer exists, so both the 0.8B and the 4B (qwen3.5:4b-mlx) are gone with it — there is no disk left to reclaim. The Homebrew CLI, ollama 0.33.0, is still installed at /opt/homebrew/bin/ollama with nothing running or stored behind it.

Deferred on purpose

Not oversights. Each of these was looked at and left alone, for a reason worth keeping.

Deferred4beb648

prewalk stays off

Prewalk switches models mid-task. The expensive model thinks and plans, then at the first file edit omp swaps to a cheap model to do the typing, so you pay premium rates only for the thinking.

It was not made the default because you can just try it per run with omp --prewalk on a real multi-file change, watch where the model badge switches, and compare against the same task without it. Turning it on globally first would be a guess about output quality, and per-turn token display had only just been switched on, so there was no baseline. The reason is written into omp/config.yml itself.

Prewalk and vibe mode do not stack. A director briefing a cheap worker that then prewalks to the same cheap model changes nothing.

Deferred—

Vibe mode and task isolation

In vibe mode your top session becomes a director that can only read files. It cannot edit. It spawns worker sessions on cheaper models to do the actual editing, then verifies by reading what they touched. That is a change to how you work, not just a setting, so it deserves its own trial. task.isolation.mode stays none, since the per-worker filesystem clones it enables only matter under vibe mode.

Deferred—

autoThinkingModel stays online

This decides which small model makes the quick "how hard should I think about this" call. Online means a remote call to Codex, which is the emptiest account at 21%, not the constrained one. Moving it local had no clear win, so the local-model work went to the tiny role instead.

A model that is offered but cannot run: omp tiny-models list shows qwen3-1.7b as disabled for local inference, because onnxruntime-node cannot run that model's export. omp still offers it as a valid value here. One of the listed options simply does not work.
Deferred—

usageReservePolicy left at confirm

This decides what happens when a fallback would land on an account that is nearly out of quota. confirm means a blocking prompt, which inside a subagent review is a hang rather than a nuisance. The other two values, auto and fail-closed, are undocumented in the installed binary. Guessing wrong either silently drains the 86%-full OpenCode Go account or hard-fails reviews that would have worked, so it is recorded as a decision for you rather than guessed at.

Still open

Two things that can still cost you. Neither was changed, because both are your call rather than a bug to fix.

Open risk—

omp approves its own shell commands, in every folder

This is the biggest remaining risk in the setup. tools.approvalMode is yolo, which auto-approves everything: running shell commands, driving a browser, spawning agents. The three modes are always-ask, which prompts before anything; write, which auto-approves reading and writing files but prompts before a shell command; and yolo.

yolo is omp's shipped default, so nobody picked it. There is a small hardcoded blocklist for things like rm -rf /, but omp's own docs say that in yolo mode a bare critical override is ignored unless you have an explicit per-tool deny rule.

It applies in every folder you open omp in. Given ~/dev holds this repo and the homelab repo, an unattended shell command in the wrong directory can cost you hours. Changing it is one line:

tools:
  approvalMode: write

How to undo any of it

Everything that touched settings is one command, because omp/config.yml is symlinked into ~/.omp/agent/. The app and the repo are the same file, so git diff shows you what omp did.

git checkout omp/config.yml            # autoqa, autolearn, interceptor,
                                      # token display, fallback order,
                                      # ignored skills, and the tiny role

git revert 7c4297a                    # adversary prompt
git revert 820f917                    # install.sh
