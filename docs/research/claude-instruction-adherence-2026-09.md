# Claude instruction adherence — what makes always-loaded instructions stick (read 2026-09-16)

Scope: primary-source Anthropic guidance (platform.claude.com/docs, code.claude.com/docs, anthropic.com/engineering, support.claude.com) on what instruction *phrasing* makes Claude reliably follow always-loaded behavioural instructions — system prompts and memory files (CLAUDE.md / AGENTS.md) — as opposed to one-off task prompts. Current model lineup per `docs/research/anthropic-models-2026-09.md`: Claude 5 family (Opus 5, Sonnet 5, Fable 5.1, Haiku 4.5), with Claude 4-generation pages (Opus 4.8 and earlier) still live as primary sources for behavioural claims Anthropic attributes to that generation. Anthropic has restructured its prompt-engineering docs since the Claude 4 era: the standalone "Claude 4 best practices" URL now 302-redirects into one combined living page, **Prompting best practices** (`claude-prompting-best-practices`), which folds "being clear and direct," multishot examples, XML tags, system prompts, long-context tips, and Claude-4-era migration advice into one document, with separate per-model pages (`prompting-claude-opus-5`, `prompting-claude-sonnet-5`, etc.) layered on top for generation-specific deltas. All pages were read 2026-09-16 unless a page's own dated content is quoted.

## Summary

- **Anthropic's own house style for behavioural instructions is direct, everyday language, not legalese or forceful emphasis.** The general guidance: "Claude responds well to clear, explicit instructions. Being specific about your desired output can help enhance results," tested against a **golden rule**: "Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too." Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (read 2026-09-16).
- **Explaining *why* an instruction matters measurably changes compliance**, per Anthropic's own before/after example: a bare "NEVER use ellipses" is "less effective" than "Your response will be read aloud by a text-to-speech engine, so never use ellipses since the text-to-speech engine will not know how to pronounce them" — "Claude is smart enough to generalize from the explanation." Source: same page (read 2026-09-16).
- **Positive framing ("do X") is documented as more reliable than negative framing ("don't do X") in three separate places**: the general docs' "Control the format of responses" technique #1 ("Tell Claude what to do instead of what not to do"), the Claude Opus 5 page ("Positive examples of the communication style you want tend to be more effective than instructions about what not to do"), and the Claude Sonnet 5 page ("Positive examples … tend to be more effective than negative examples or instructions that tell the model what not to do"). Sources: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5, https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5 (all read 2026-09-16).
- **CLAUDE.md is documented, not just inferred, as sensitive to length and specificity, with an explicit size ceiling**: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence," and "The more specific and concise your instructions, the more consistently Claude follows them." Source: https://code.claude.com/docs/en/memory (read 2026-09-16).
- **Bloat is documented as actively harmful, not just wasteful**: "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" and the named failure pattern "The over-specified CLAUDE.md. If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise." Source: https://code.claude.com/docs/en/best-practices (read 2026-09-16).
- **Anthropic frames context length degradation as a general transformer property, not folklore**, citing external research: "Studies on needle-in-a-haystack style benchmarking have uncovered the concept of context rot: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases," citing `research.trychroma.com/context-rot`. Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (read 2026-09-16).
- **The "right altitude" is Anthropic's own named heuristic for instruction specificity**: not "hardcoding complex, brittle logic" and not "vague, high-level guidance that fails to give the LLM concrete signals" — instead "specific enough to guide behavior effectively, yet flexible enough to provide the model with strong heuristics." Source: same page (read 2026-09-16).
- **Conflicting instructions across files are documented to resolve arbitrarily, not gracefully**: "if two rules contradict each other, Claude may pick one arbitrarily." Source: https://code.claude.com/docs/en/memory (read 2026-09-16).
- **Emphasis words are documented to work only when scarce**: "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." Source: https://code.claude.com/docs/en/best-practices (read 2026-09-16).
- **Aggressive/urgent phrasing is documented to backfire on current models by causing overtriggering, not better compliance**: "Where you might have said 'CRITICAL: You MUST use this tool when…', you can use more normal prompting like 'Use this tool when…'." Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (read 2026-09-16).
- **Claude Sonnet 5 is documented as more literal than its predecessor specifically**: "Claude Sonnet 5 interprets prompts literally and explicitly, particularly at lower effort levels. It does not silently generalize an instruction from one item to another, and it does not infer requests you didn't make. … If you need Claude to apply an instruction broadly, state the scope explicitly." Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5 (read 2026-09-16).
- **Proximity/recency inside a long prompt is documented as a real lever, twice**: general long-context guidance says queries placed after long reference material "can improve response quality by up to 30 percent in tests," and the Opus 5 page recommends pairing a length/tone instruction with "a short reminder near the end of the prompt" when the system prompt is long. Sources: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5 (both read 2026-09-16).
- **CLAUDE.md is not part of the system prompt and compliance is explicitly not guaranteed**: "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance, especially for vague or conflicting instructions." Source: https://code.claude.com/docs/en/memory (read 2026-09-16).
- **Anthropic's own maintenance advice for CLAUDE.md treats it as an evals-tested artifact, not static prose**: "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts," with a one-line litmus test per entry: "Would removing this cause Claude to make mistakes?" Source: https://code.claude.com/docs/en/best-practices (read 2026-09-16).

## What Anthropic documents as working

- **Clarity and directness, benchmarked against a naive reader.** "Think of Claude as a brilliant but new employee who lacks context on your norms and workflows. The more precisely you explain what you want, the better the result," with the golden-rule test of showing the prompt to a minimally-briefed colleague. Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (read 2026-09-16). Applies to all current models per the page's own scope statement.
- **Sequential/numbered steps when order or completeness matters.** "Provide instructions as sequential steps using numbered lists or bullet points when the order or completeness of steps matters." Source: same page (read 2026-09-16).
- **Explaining the motivation behind a rule, not just the rule.** "Providing context or motivation behind your instructions, such as explaining to Claude why such behavior is important, can help Claude better understand your goals and deliver more targeted responses." Demonstrated with the ellipses/text-to-speech example above. Source: same page (read 2026-09-16).
- **Positive, concrete instructions over prohibitions.** Documented three times independently (general docs, Opus 5 page, Sonnet 5 page) — see Summary. This is the single most consistently repeated actionable claim found across the docs.
- **Sectioned, tagged structure for anything non-trivial.** The context-engineering blog: "organizing prompts into distinct sections (like `<background_information>`, `<instructions>`, `## Tool guidance`, `## Output description`, etc.) and using techniques like XML tagging or Markdown headers to delineate these sections." The prompting-best-practices page adds: "Use consistent, descriptive tag names across your prompts," and "Nest tags when content has a natural hierarchy." Sources: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents, https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (both read 2026-09-16). CLAUDE.md-specific guidance echoes this at Markdown-header granularity: "use markdown headers and bullets to group related instructions. Claude scans structure the same way readers do: organized sections are easier to follow than dense paragraphs." Source: https://code.claude.com/docs/en/memory (read 2026-09-16).
- **Right-altitude specificity: concrete and verifiable, not prescriptive procedure.** CLAUDE.md docs give three paired examples: "'Use 2-space indentation' instead of 'Format code properly'"; "'Run `npm test` before committing' instead of 'Test your changes'"; "'API handlers live in `src/api/handlers/`' instead of 'Keep files organized.'" Source: https://code.claude.com/docs/en/memory (read 2026-09-16). The engineering blog frames the same idea at the system-prompt level: aim for "the minimal set of information that fully outlines your expected behavior," while cautioning "minimal does not necessarily mean short; you still need to give the agent sufficient information up front." Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (read 2026-09-16).
- **An explicit litmus test for whether a line belongs in an always-loaded file.** "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it." Paired with an include/exclude table: include bash commands Claude can't guess, non-default code style, testing instructions, repo etiquette, architectural decisions, environment quirks, non-obvious gotchas; exclude anything derivable from reading the code, standard conventions, long explanations/tutorials, and "self-evident practices like 'write clean code'." Source: https://code.claude.com/docs/en/best-practices (read 2026-09-16).
- **Emphasis words work only when rare.** "If Claude keeps skipping one instruction, add emphasis such as 'IMPORTANT' to that line alone. If you emphasize many lines, none of them stands out." Source: same page (read 2026-09-16).
- **Motivation/context transfers to tool- and agent-level instructions, not just prose rules.** Anthropic's tool-design guidance uses the identical "new hire" framing as the prompting docs: "think of how you would describe your tool to a new hire on your team. Consider the context that you might implicitly bring … and make it explicit." Source: https://www.anthropic.com/engineering/writing-tools-for-agents (read 2026-09-16). This is the same underlying claim (make implicit context explicit) restated for a different artifact, which strengthens rather than duplicates the evidence.
- **Examples over abstract description, when the example set is small and diverse.** "A few well-crafted examples (known as few-shot or multishot prompting) improve accuracy and consistency," with guidance to keep them relevant, diverse (to avoid the model "picking up unintended patterns"), and structured in `<example>` tags; "Include 3–5 examples for best results." Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (read 2026-09-16).
- **A minimal role/system-prompt sentence measurably focuses tone and behavior.** "Setting a role in the system prompt focuses Claude's behavior and tone for your use case. Even a single sentence makes a difference." Source: same page (read 2026-09-16).
- **Consistency checks are an explicit maintenance step, not a one-time authoring concern.** "Review your CLAUDE.md files, nested CLAUDE.md files in subdirectories, and `.claude/rules/` periodically to remove outdated or conflicting instructions." Source: https://code.claude.com/docs/en/memory (read 2026-09-16).
- **Iterative, evals-driven tuning, not one-shot authorship.** The engineering blog recommends "testing a minimal prompt with the best model available and iteratively adding clear instructions and examples to steer behavior where the agent doesn't do what you want," i.e. start minimal, add only to fix an observed failure mode. Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (read 2026-09-16). The Claude Code docs restate this as maintenance discipline: "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." Source: https://code.claude.com/docs/en/best-practices (read 2026-09-16).
- **Proximity of an instruction to the point of generation helps on long prompts.** Two independent, model/context-agnostic-in-spirit statements: general long-context guidance — "Place your long documents and inputs near the top of your prompt, above your query, instructions, and examples… Queries at the end can improve response quality by up to 30 percent in tests, especially with complex, multidocument inputs" — and the Opus 5 page's concrete pattern for a long system prompt: state the main instruction once, then "pair the instruction with a short reminder near the end of the prompt," e.g. a short `<tone_preference>` tag. Sources: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices, https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5 (both read 2026-09-16).
- **Explicit scope statements when a rule should generalize.** Sonnet 5's literalism means a rule stated for one case is not assumed to extend to others: "state the scope explicitly (for example, 'Apply this formatting to every section, not just the first one')." Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5 (read 2026-09-16).
- **Concrete alternatives beat generic prohibitions for steering default output style.** On design/frontend defaults: "Generic instructions ('don't use that color,' 'make it clean and minimal') tend to shift the model to a different fixed palette rather than producing variety," whereas specifying a concrete alternative (exact palette, typography, layout) "follows explicit specs precisely." Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5 (read 2026-09-16). This is a generation-specific (Sonnet 5) restatement of the general positive-framing finding, in a domain (visual style) closely analogous to the "outcome-focused, not code-focused" plan-writing ask in scope for this research.
- **`AGENTS.md`/import compatibility is explicitly supported, not merely tolerated**, which is directly relevant to a harness-neutral file: "Claude Code reads `CLAUDE.md`, not `AGENTS.md`. If your repository already uses `AGENTS.md` for other coding agents, create a `CLAUDE.md` that imports it," via `@AGENTS.md` import or a symlink. Source: https://code.claude.com/docs/en/memory (read 2026-09-16).

## What degrades adherence

- **Length/bloat, documented with a specific numeric threshold.** "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence" and "Files over 200 lines consume more context and may reduce adherence." Source: https://code.claude.com/docs/en/memory (read 2026-09-16). The best-practices page states the mechanism-level consequence more bluntly: "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Source: https://code.claude.com/docs/en/best-practices (read 2026-09-16).
- **Vagueness.** The Claude Code troubleshooting flow for "Claude isn't following my CLAUDE.md" leads first with specificity: "Make instructions more specific. 'Use 2-space indentation' works better than 'format code nicely'," and separately: "there's no guarantee of strict compliance, especially for vague or conflicting instructions." Source: https://code.claude.com/docs/en/memory (read 2026-09-16). At the system-prompt level, the engineering blog names the same failure symmetrically to over-specification: "vague, high-level guidance that fails to give the LLM concrete signals for desired outputs or falsely assumes shared context." Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (read 2026-09-16).
- **Conflicting instructions resolve arbitrarily, not by some priority Claude infers.** "if two rules contradict each other, Claude may pick one arbitrarily," and in troubleshooting: "Look for conflicting instructions across CLAUDE.md files. If two files give different guidance for the same behavior, Claude may pick one arbitrarily." Source: https://code.claude.com/docs/en/memory (read 2026-09-16).
- **Context rot as input length grows, attributed to transformer architecture and external benchmarking, not Anthropic's own claim alone.** "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases," rooted in "the transformer architecture's n² pairwise token relationships" — "models remain highly capable at longer contexts but may show reduced precision for information retrieval and long-range reasoning compared to their performance on shorter contexts." Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (read 2026-09-16), citing `research.trychroma.com/context-rot` (not independently verified in this research pass — Anthropic is the primary source cited here, not the Chroma study itself).
- **Over-specified, brittle instructions are a named failure mode, symmetric to vagueness.** "engineers hardcoding complex, brittle logic in their prompts to elicit exact agentic behavior. This approach creates fragility and increases maintenance complexity over time." Source: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents (read 2026-09-16). The Claude Code best-practices page gives the operational version: "The over-specified CLAUDE.md. If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise. Fix: Ruthlessly prune." Source: https://code.claude.com/docs/en/best-practices (read 2026-09-16).
- **Negative/prohibition framing is documented as *less* effective than positive framing, repeatedly, though never stated as a hard rule that negation itself fails.** See the three citations under "What Anthropic documents as working" (ellipses example; Opus 5 and Sonnet 5 pages both say positive examples outperform negative ones for shaping communication style). No page states that negation *never* works — the Opus 5 subagent-spawning and code-review prompts in the same doc set do include "Do not …" clauses that Anthropic itself recommends — so the documented claim is a *reliability/consistency* difference (positive framing generalizes and steers style more predictably), not an absolute prohibition on negation.
- **Aggressive/urgent emphasis causes overtriggering on current models, which is a documented regression from earlier prompting habits, not a neutral no-op.** "Claude Opus 4.5 and Claude Opus 4.6 are also more responsive to the system prompt than previous models. If your prompts were designed to reduce undertriggering on tools or skills, these models may now overtrigger. The fix is to dial back any aggressive language." Source: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (read 2026-09-16). This is documented for the Claude 4-generation transition (Opus 4.5/4.6) specifically, not asserted for Claude 5.
- **CLAUDE.md's own delivery mechanism is a structural ceiling on adherence**, independent of phrasing quality: "CLAUDE.md content is delivered as a user message after the system prompt, not as part of the system prompt itself. Claude reads it and tries to follow it, but there's no guarantee of strict compliance." Source: https://code.claude.com/docs/en/memory (read 2026-09-16). Practical corollary Anthropic gives for anything that must be deterministic: "If the instruction is something that must run at a specific point … write it as a hook instead. Hooks execute as shell commands at fixed lifecycle events and apply regardless of what Claude decides to do." Source: same page (read 2026-09-16). **Inference:** a "Plans" section describing a *stylistic/communication* preference cannot be made deterministic this way — hooks apply to actions, not prose style — so its reliability ceiling is whatever prompt-phrasing quality can buy, not enforcement.
- **Repeated correction in one session is itself diagnostic of a prompt/context problem, not something to push through.** "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." Source: https://code.claude.com/docs/en/best-practices (read 2026-09-16).
- **Ambiguous phrasing produces silent misreads, not visible failures.** "If Claude asks you questions that are answered in CLAUDE.md, the phrasing might be ambiguous." Source: same page (read 2026-09-16).

## Unsupported or folklore

The following are commonly repeated in prompt-engineering discussion but could **not** be traced to any Anthropic primary source across the pages fetched for this research (prompt-engineering docs and sub-pages, Claude 4/5 model-specific pages, Claude Code memory/best-practices docs, the effective-context-engineering and writing-tools-for-agents engineering posts):

- **"Tipping" or reward/threat framing improves compliance** (e.g. "I'll tip you $200 for a great answer," or threats of consequences for non-compliance). Searched the prompt-engineering best-practices page, the Claude 4/5 model pages, and the context-engineering blog; none mention incentive framing at all, positively or negatively. Not supported either way by anything found.
- **Repeating the same instruction multiple times in a prompt increases compliance in general** (as a blanket technique, distinct from the specific "near-the-top reminder near the end" pattern Anthropic documents for Opus 5's one instruction on tone in a long system prompt). No page generalizes this into "repeat instructions for emphasis" as a technique; the only "repeat near the end" pattern found is scoped to that one Opus-5 example.
- **ALL CAPS or exclamation marks make Claude take an instruction more seriously.** Not found; the closest primary-source statement is the opposite direction — dialing back aggressive/urgent language like "CRITICAL: You MUST" reduces *overtriggering* on current models rather than improving compliance. This is refuted rather than merely unsupported.
- **"Think step by step" as a magic incantation that reliably improves reasoning on current models.** Not supported as a general technique for current (adaptive-thinking) models; the current docs instead say "Prefer general instructions over prescriptive steps. A prompt like 'think thoroughly' often produces better reasoning than a hand-written step-by-step plan," and frame manual chain-of-thought tagging (`<thinking>`/`<answer>`) as a fallback only for models/configurations with thinking disabled. Source for the superseding claim: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (read 2026-09-16).
- **A specific numeric word-count or sentence-count cap (e.g. "in under 3 sentences") is more reliable than a qualitative brevity instruction ("be concise").** Anthropic's own conciseness examples in the docs (Opus 5, Sonnet 5) use qualitative phrasing ("Keep responses focused, brief, and concise," "Provide concise, focused responses") rather than hard numeric caps, and no page states that a numeric cap outperforms a qualitative one. Absence of a claim either way; not confirmed.
- **Placing instructions at the very beginning of a system prompt (as opposed to the end) is better for general behavioral rules**, as a blanket claim. What is documented is narrower and sometimes points the other way: long reference *data* belongs at the top with the *query* at the end (long-context guidance), and a specific tone reminder belongs restated *near the end* of a long system prompt (Opus 5 guidance) — neither of these generalizes cleanly to "put your important rule first" for a short, always-loaded preferences file, and no page makes that broader claim directly.

## Implications for an always-loaded preferences file

These are concrete rewrites for a `## Plans` (or similar) section of `global-agents.md`, each tied to a specific finding above:

1. **State the outcome positively, not as a prohibition.** Replace anything shaped like "don't describe code" or "avoid technical jargon" with a direct statement of what the plan *should* be: e.g. "Describe the plan as user-facing outcomes in plain English." This follows the repeated (general docs + Opus 5 + Sonnet 5) finding that positive framing is more reliably followed and generalizes better than negative framing.
2. **Give one line of *why*, not just the rule**, mirroring the documented ellipses example: state who reads the plan and what breaks if it's code-heavy (e.g., "the user reviewing this can't read diffs, so...") rather than a bare style directive. Anthropic states Claude "is smart enough to generalize from the explanation" — the reason does the steering work a longer rule list would otherwise have to do.
3. **Make the instruction concrete and checkable, not aspirational.** Use the CLAUDE.md pattern of paired concrete/vague examples: prefer something like "name the screens/behaviors that change and what the user will see differently" over "focus on user-facing outcomes," which is the vaguer of the two framings even though it sounds specific. Concreteness is what the docs' own before/after pairs optimize for.
4. **Keep it short and isolated from unrelated rules**, and don't over-qualify it with edge cases. The documented 200-line ceiling and "bloated files cause Claude to ignore your actual instructions" apply to the whole file, but the "over-specified CLAUDE.md" and "right altitude" failure modes apply per-section too: a `## Plans` section with many hedges and exceptions is the brittle-hardcoded-logic failure mode the context-engineering blog warns about. Aim for the "minimal set of information that fully outlines your expected behavior" for this one behavior, not a policy document.
5. **State scope explicitly if the rule should generalize across situations** (e.g., whether "plain English, no code" applies to every plan regardless of size, or only to plans presented to the user versus internal scratch notes) — Sonnet 5's documented literalism means an unstated scope is not assumed to extend beyond the example given.
6. **Reserve emphasis (`IMPORTANT`, bold, all-caps) for at most one place in the whole file, and not on this section unless it's demonstrably being skipped.** The docs are explicit that emphasis works by scarcity ("If you emphasize many lines, none of them stands out") and that current models overtrigger on urgent language ("CRITICAL: You MUST") rather than comply better.
7. **If Claude keeps writing code-heavy plans despite this section, treat that as a signal the file is too long or the phrasing is ambiguous, not a reason to add more forceful wording.** Per the documented troubleshooting flow: first check the instruction loaded (`/context`), then make it more specific/concrete, then check for a conflicting instruction elsewhere in the file (e.g., a coding-workflow section that implicitly asks for a code-first walkthrough) before adding emphasis.
8. **Treat this section as a tested artifact, not a one-time edit.** Anthropic's own recommended workflow is iterative: change the line, then observe whether the model's actual plan output shifts, and prune or rephrase if it doesn't — "test changes by observing whether Claude's behavior actually shifts."
9. **Don't expect this instruction to be enforced deterministically.** Because it governs a communication *style* rather than a gateable action, it cannot be moved to a hook (hooks fire on tool/lifecycle events, not on the shape of prose); its reliability ceiling is bounded by phrasing quality alone, which raises the value of doing 1–8 well rather than treating any one rewrite as a guaranteed fix.
10. **Do not rely on repetition, reward/tip language, or urgency markers as a fallback if the plain rewrite underperforms** — none of these are documented techniques, and urgency is documented to backfire; if the concrete/positive rewrite still doesn't stick, the documented next steps are check-for-conflicts and simplify, not escalate the language.
