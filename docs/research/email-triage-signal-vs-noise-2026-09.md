# Separating signal from noise in a mixed Gmail inbox: deterministic headers, platform signals, proven product patterns, and a Jev cascade (2026-09-28)

All pages read 2026-09-28 unless noted. Every claim carries its source URL. No mailbox
content, sender addresses, or subjects from the user's account appear anywhere below —
only public vendor/RFC documentation and the user's own workflow's *code and prompt
text* (read from `~/Desktop/JevClassify-openrouter.json`, not modified). Anything not
directly stated by a primary source is tagged **[INFERENCE]**.

## Summary

- **Deterministic header signals are real but weaker than they look.** RFC-level
  headers (`List-Unsubscribe`, `List-Id`, `Auto-Submitted`) are self-asserted by the
  sending software with no cryptographic guarantee; only `Authentication-Results`
  (when stamped by Gmail's own receiving MTA) plus DMARC alignment gives a
  verifiable identity claim. `Precedence: bulk` is not standardized by any RFC — the
  RFCs that mention it say so explicitly. None of this is currently sent to Jev: the
  workflow's `state` carries only `from/to/date/subject/body/gmail_signals`, so the
  entire deterministic layer is unused today.
- **Since Feb 2024, Gmail requires bulk senders (≥5,000 msgs/day) to publish SPF+DKIM+DMARC
  and support RFC 2369/8058 one-click unsubscribe.** That means, in 2026, a message that
  is missing these — no `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, no aligned
  DMARC pass — is now unusual for a *large legitimate marketer* specifically, and this
  gap is itself a moderately strong pre-model signal, cheap to compute, that the current
  workflow does not use.
- **Gmail's own `CATEGORY_*`/`IMPORTANT` labels are behavioral/adaptive predictions, not
  ground truth**, and Google's own docs frame them that way (per-user learned signals,
  explicit user opt-out). The workflow already passes `CATEGORY_*`/`IMPORTANT` into
  `gmail_signals`, and the existing prompt correctly calls this "weak supporting
  evidence only" — that framing is right per Google's own documentation.
- **Every mature triage product's real innovation is a per-sender decision cached
  forever, not a per-message classification.** HEY's Screener, Gmail's own new "Manage
  subscriptions" view, SaneBox's BlackHole, Superhuman's VIP/Team, Shortwave's
  auto-apply-per-sender labels, and Apple Mail VIP all converge on the same principle:
  classify the *sender* once, and let it silently answer every subsequent message. The
  current workflow classifies every message from scratch, forever, even for senders it
  has already seen 50 times.
- **TypeSafe's own material (Jev docs + OpenRouter's "Classify and Tag Text at Scale
  with Jev" cookbook) prescribes exactly the multi-Noul-question design this project
  is considering**, and gives an explicit, numeric procedure for picking thresholds
  from a 100–200-item hand-labeled sample (precision/recall sweep for Noul tags,
  confidence-band accuracy table for the Choice). Neither TypeSafe nor OpenRouter
  documents any per-sender caching of verdicts — that idea is sound but is this
  document's **[INFERENCE]**, not a vendor recommendation.
- **Gmail already blocks >99.9% of spam/phishing/malware before anything reaches the
  inbox** (Google's own headline safety statistic). What still lands in "has:nouserlabels"
  and reaches Jev is, by construction, mail that survived Gmail's own filter — a small
  probabilistic decision model should never be asked to be the last phishing gate;
  authentication results plus lookalike-domain checks are the primary defense, and Jev
  (if used at all here) should be a second-opinion escalator to Needs Review, never an
  auto-clear.

## 1. Deterministic header signals before any model

None of the following headers are in the workflow's current `state` payload (confirmed
by reading the `jsonBody` template in the Classify Email with Jev node: only
`from, to, date, subject, body, gmail_signals`).

### List-Unsubscribe / List-Unsubscribe-Post (RFC 2369, RFC 8058)

- RFC 2369 defines `List-Unsubscribe` (plus `List-Help`, `List-Subscribe`, `List-Post`,
  `List-Owner`, `List-Archive`) and states these fields "MUST only be generated by
  mailing lists, not end users" — presence signals list-management *software*, not a
  human. https://www.rfc-editor.org/rfc/rfc2369 (read 2026-09-28).
- RFC 8058 adds `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, and requires the
  message to carry "a valid DKIM signature" whose `h=` tag covers both headers —
  "If the message does not have the required DKIM signature, the mail receiver SHOULD
  NOT offer a one-click unsubscribe." https://www.rfc-editor.org/rfc/rfc8058 §3.1, §4
  (read 2026-09-28).
- **What it proves:** a DKIM-covered `List-Unsubscribe-Post=One-Click` pair is strong
  evidence of ESP/marketing-platform tooling, because that tooling exists specifically
  to satisfy this RFC pair and Gmail's bulk-sender rule (next section).
- **What it does not prove:** legitimacy. RFC 8058 §6 itself warns "a malicious mailer
  could send spam with content intended to provoke large numbers of unsubscriptions and
  with suitably crafted headers" — the header signals *bulk/list machinery*, not
  *trustworthiness*.
- **Reliability, transactional vs. marketer:** a transactional sender (bank, OTP
  service) has no protocol reason to emit `List-Unsubscribe` (nothing to unsubscribe
  from); a compliant bulk marketer, per Gmail's 2024 rule (below), is now required to.
  Absence is a moderately good "probably not commercial bulk mail" signal; presence
  paired with valid DKIM coverage is a moderately good "definitely bulk/list mail"
  signal.

### List-Id (RFC 2919)

- Defines `List-Id` as a persistent, domain-namespaced identifier for a mailing list,
  independent of which host currently serves it — "This field MUST only be generated
  by mailing list software, not end users." https://www.rfc-editor.org/rfc/rfc2919 §3
  (read 2026-09-28).
- **What it does not prove:** no cryptographic tie between the `List-Id` string and any
  organization (self-asserted); does not distinguish marketing from legitimate
  discussion lists — both use the same header.
- **Reliability:** transactional senders have no reason to emit it (it identifies
  *list* traffic specifically); its presence is a reasonably strong signal of
  bulk/list software, weak on its own for marketing-vs-not.

### Auto-Submitted (RFC 3834)

- "The Auto-Submitted field, with a value of 'auto-replied', SHOULD be included in the
  message header of any automatic response," and "no" (or absence) is the default for
  ordinary human mail. https://www.rfc-editor.org/rfc/rfc3834 §3.1.7, §2 (read
  2026-09-28).
- **What it does not prove:** it is a SHOULD, not a MUST, aimed at auto-responders
  (vacation replies, service bots) — most marketing platforms never set it at all, so
  its *absence* does not imply a human sender.

### Precedence: bulk

- **Not standardized by any RFC.** RFC 2076 ("Common Internet Message Headers") is
  Informational only ("This memo does not specify an Internet standard of any kind")
  and simply catalogs the header as observed in the wild.
  https://www.rfc-editor.org/rfc/rfc2076 (read 2026-09-28).
- RFC 3834 itself says: "Because Precedence is not a standard header field, and its use
  and interpretation vary widely in the wild, no particular responder behavior in the
  presence of Precedence is recommended by this specification."
  https://www.rfc-editor.org/rfc/rfc3834 §2 (read 2026-09-28).
- **Reliability:** low and RFC-acknowledged as such. Use only as a weak tiebreaker,
  never as a standalone bulk/marketing signal.

### Authentication-Results / SPF / DKIM / DMARC and alignment (RFC 8601, 7208, 6376, 7489)

- RFC 8601 defines `Authentication-Results` as a machine-readable summary stamped by
  the *receiving* MTA. Critically: "the mere presence of this header field does not
  mean its contents are valid... there must be an assessment of the trust relationship"
  between the reader and the stamping MTA. https://www.rfc-editor.org/rfc/rfc8601 §1.2
  (read 2026-09-28). **Implication for this workflow:** the header is only trustworthy
  when it is the copy stamped by Gmail's own receiving infrastructure — which is
  exactly the copy the Gmail API exposes, so this is safe to trust here, but would not
  be safe to trust on an arbitrarily forwarded/relayed message.
- RFC 7208 (SPF) authenticates only the envelope `MAIL FROM`/`HELO` identity, not the
  visible `From:` header the user reads. https://www.rfc-editor.org/rfc/rfc7208 (read
  2026-09-28).
- RFC 6376 (DKIM) proves the signed content was untampered and that the `d=` signing
  domain authorized it — explicitly *not* that `d=` matches the visible `From:` domain
  ("the signing identity specified by a DKIM signature is not required to match an
  address in any particular header field," §1.2).
  https://www.rfc-editor.org/rfc/rfc6376 (read 2026-09-28).
- RFC 7489 (DMARC, Informational, not Standards Track) is what closes that gap:
  "Identifier Alignment" means "the domain in the RFC5322.From address matches a domain
  validated by SPF or DKIM (or both)" (§3.1). DMARC explicitly does **not** address
  "visually similar domain names ('cousin domains') or abuse of the ... human-readable
  <display-name>" (§2.4) — i.e., it stops exact-domain spoofing only, not lookalikes.
  https://www.rfc-editor.org/rfc/rfc7489 (read 2026-09-28).
- **Reliability:** this is the one deterministic layer with a real trust anchor (Gmail's
  own MTA stamp) and the one that should carry the most weight — but only for
  exact-domain spoofing; lookalike domains need a separate check (§5 below).

### Gmail's 2024+ bulk-sender requirements

- From the official page: "Starting February 1, 2024, all email senders who send email
  to Gmail accounts must meet [baseline] requirements... email senders who send more
  than 5,000 messages per day to Gmail accounts must meet [additional] requirements."
  Baseline: SPF or DKIM, valid PTR records, TLS, Postmaster spam rate < 0.3%, RFC 5322
  formatting. Bulk tier (≥5,000/day): SPF **and** DKIM, DMARC, DMARC-aligned From:
  domain, and "Marketing messages and subscribed messages must support one-click
  unsubscribe, and include a clearly visible unsubscribe link in the message body,"
  implemented via the exact `List-Unsubscribe`/`List-Unsubscribe-Post` pair from RFC
  2369/8058 (Google's page cites both RFCs directly).
  https://support.google.com/mail/answer/81126 (read 2026-09-28).
- **Consequence:** in 2026, a message from a domain sending real marketing volume that
  is *missing* SPF+DKIM+DMARC+one-click-unsubscribe is now either a small/non-compliant
  sender or is misrepresenting itself — this gap is a usable, cheap pre-model signal
  that did not exist before Feb 2024.

### Reading these headers from the Gmail API and from n8n

- `users.messages.get` accepts `format` and a repeated `metadataHeaders[]` parameter:
  "When given and format is `METADATA`, only include headers specified."
  https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/get
  (read 2026-09-28). The `Format` enum: `metadata` = "Returns only email message ID,
  labels, and email headers" (no body).
  https://developers.google.com/workspace/gmail/api/reference/rest/v1/Format (read
  2026-09-28). This is the officially documented, cheap way to pull just
  `List-Unsubscribe`, `List-Id`, `Authentication-Results`, etc. before ever reading a
  message body.
- n8n's own Gmail node docs state: "**Simplify**: Choose whether to return a simplified
  version of the response (turned on) or the raw data (turned off)... This is the same
  as setting the `format` for the API call to `metadata`, which returns email message
  IDs, labels, and email headers, including: From, To, CC, BCC, and Subject."
  https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.gmail/message-operations
  (read 2026-09-28). **Gap:** n8n's docs describe only the Simplify=**on** behavior in
  that much detail; they do not enumerate which fields Simplify=**off** (what this
  workflow currently uses, `"simple": false`, confirmed by reading the workflow JSON)
  returns. **Verified empirically 2026-09-28:** the saved output of the homelab n8n
  execution 49145 (`Fetch Unlabelled Emails`, `simple:false`) has a `headers` object
  keyed by lowercase header name (`authentication-results`, `received-spf`,
  `dkim-signature`, `feedback-id`, `return-path`, …) alongside `text`, `html` and
  `labelIds`. Only the first item's key names were inspected, no message content; that
  message was a Google account notice with no list headers, so `list-unsubscribe` /
  `list-id` appearing under the same object when a sender sets them is **[INFERENCE]**.
  The headers are already fetched and discarded, so a header pre-filter is a new
  parsing step in the existing flow, not a new API round trip.

## 2. Gmail's built-in signals

- **`CATEGORY_PERSONAL/SOCIAL/PROMOTIONS/UPDATES/FORUMS`**: the Gmail API guide states
  each "corresponds to messages that are displayed in the [X] tab of the Gmail
  interface," and all five can be applied manually via the API.
  https://developers.google.com/workspace/gmail/api/guides/labels (read 2026-09-28).
  Google's own end-user description: Promotions = "Deals, offers, and other
  promotional emails"; Updates = "Automated confirmations, notifications, statements,
  and reminders that may not need immediate attention"; Forums = "Messages from online
  groups, discussion boards, and mailing lists." Moving mail between tabs "helps Gmail
  learn your preferences and sort your email more accurately over time" — i.e. this is
  an adaptive, per-user, behaviorally-trained signal.
  https://support.google.com/mail/answer/3094499 (read 2026-09-28).
- **`IMPORTANT`**: Google's own documented signal list is behavioral, not editorial —
  "Whom you email, and how often," "Which emails you open," "Which emails you reply
  to," keyword patterns, and star/archive/delete history.
  https://support.google.com/mail/answer/186543 (read 2026-09-28). Google itself offers
  an explicit opt-out ("Don't use my past actions to predict which messages are
  important") — Google's own acknowledgment that this is a prediction a user may
  distrust, not ground truth. No primary Google sentence explicitly warns integrators
  against trusting `IMPORTANT` alone; that caution is this document's own conclusion
  from the signal list plus the opt-out affordance.
- **`SPAM`**: "As you report more spam, Gmail identifies similar emails as spam more
  efficiently." Google documents specific reasons mail lands in Spam (spoofed
  addresses, phishing, unconfirmed/failed-auth senders, empty content used to probe
  live addresses, volume attacks) and an explicit false-positive path (removable,
  fixable by adding to Contacts) plus an explicit override: once a sender is blocked,
  "even when you remove their emails from Spam, Gmail still automatically identifies
  their emails as spam." https://support.google.com/mail/answer/1366858 (read
  2026-09-28). No numeric false-positive/false-negative rate is published anywhere
  found in primary Google sources — only this qualitative language.
- **Trustworthiness for this workflow:** all of `CATEGORY_*`/`IMPORTANT` are legitimate
  *weak features* (Google's own docs frame them as adaptive predictions) but none of
  them is a final decision — matching the existing prompt's own framing ("weak
  supporting evidence only"), which this research validates rather than contradicts.

## 3. Proven product patterns: per-sender beats per-message

Every mechanism below is vendor-documented (not third-party review); the pattern that
recurs is **decide about the sender once, cache the decision, stop asking**.

- **HEY Screener**: "When someone emails your @hey.com address for the very first time,
  they don't get straight through, they land in The Screener. This is where you decide
  if you want to hear from them or not." The decision persists per-sender or per-domain
  and applies to all future mail without re-prompting; adding someone to Contacts
  auto-approves them. https://www.hey.com/how-it-works/,
  https://help.hey.com/article/722-the-screener (read 2026-09-28).
- **Gmail's own "Manage subscriptions"** (rolled out from mid-2025): "you'll find your
  active subscriptions sorted by the most frequent senders... Easily unsubscribe in one
  click, and Gmail will send an unsubscribe request to the sender on your behalf."
  Gmail explicitly separates "unsubscribe" (stop the list) from "block" (stop the
  sender entirely, straight to Spam) as two distinct sender-scoped actions.
  https://support.google.com/mail/answer/15621070,
  https://blog.google/products-and-platforms/products/gmail/new-manage-subscriptions-unsubscribe/
  (read 2026-09-28).
- **SaneBox**: layers *on top of* existing filters ("Your Gmail filters will continue
  working as usual! They run before SaneBox even sees your messages"), and turns a
  single manual drag of one message into a durable per-sender rule ("Sane DIY
  Training... Move example messages into the folder and SaneBox will learn where
  similar email belongs"; "SaneBlackHole... moves current and future Inbox emails from
  an unwanted sender"). It also surfaces a crowdsourced, cross-user "popular candidate
  for BlackHole" nudge that still requires the individual user's confirming click — a
  suggestion, not an autonomous action. https://www.sanebox.com/help/159-...,
  https://www.sanebox.com/help/138-what-is-a-feature,
  https://www.sanebox.com/release-notes (read 2026-09-28).
- **Superhuman Split Inbox**: rule-first, sender/domain-based buckets ("Important
  contains all person-to-person and high-priority messages, while Other contains
  emails sent to mailing lists, and automated messages") plus a VIP bucket and an
  explicit correction flow for misrouted mail.
  https://help.superhuman.com/hc/en-us/articles/46005619081101-Default-Split-Inbox
  (read 2026-09-28).
- **Shortwave**: natural-language AI filters plus an explicit "set labels to be
  automatically applied or removed on a per-sender basis... let Shortwave handle the
  rest," and a dry-run "Reapply filters" step "to see exactly what actions the AI takes
  and why" before trusting it at scale.
  https://www.shortwave.com/docs/guides/customize-your-shortwave-settings/ (read
  2026-09-28).
- **Apple Mail VIP**: a per-sender tag usable everywhere (mailbox view, search ranking,
  filter rules), synced at the account level.
  https://support.apple.com/guide/icloud/make-a-sender-a-vip-mma27f86124d/icloud (read
  2026-09-28).

**Transferable principle, stated once because every vendor converges on it:** a
per-sender verdict, made once (by a human, the model, or crowdsourced behavior) and
cached indefinitely, collapses an unbounded message stream into a small, shrinking set
of first-contact decisions. The current n8n workflow has no notion of "sender" at all —
every message, including the 50th from the same newsletter, is independently sent to
Jev.

## 4. Cascade design with Jev

- **Three primitives, explicitly mixable and parallel:** "All three question types can
  be mixed in a single API call. Every question is evaluated in parallel and in
  isolation against the same state in one go... Each question is evaluated
  independently, so adding more questions does not create context-rot."
  https://docs.typesafe.ai/introduction (read 2026-09-28). The docs also directly
  instruct atomicity: "System One models work best when each question asks one
  specific, well-scoped thing... If the question you want to ask would require
  extended reasoning or weighs multiple independent factors, decompose it. Ask each
  factor as a separate question, then combine the results with logic in your code."
  https://docs.typesafe.ai/introduction (read 2026-09-28).
- **Multiple independent Noul questions in one request is the vendor-sanctioned
  pattern, not a novel idea:** TypeSafe's own Noul primitive page's worked example
  sends two separate Noul questions ("is_human_escalation", "is_repeat_contact")
  against one shared state in a single call. https://docs.typesafe.ai/primitives/noul
  (read 2026-09-28). The "Speculative Fan-Out" pattern page goes further: "we recommend
  putting all of the questions your system needs in a single request, and then using
  code to decide what is relevant after the fact." https://docs.typesafe.ai/patterns/fan-out
  (read 2026-09-28). This directly supports adding separate Noul questions for
  "bulk/marketing," "from a real human," "transactional about the recipient's own
  account," and "phishing" alongside the existing `label`/`needs_reply` pair, in the
  same request, at effectively no added latency.
- **The OpenRouter cookbook "Classify and Tag Text at Scale with Jev" is exactly this
  workflow's shape** — one exclusive `choice` category plus one `noul` per tag —
  applied at 550-item batch scale on the public TweetTopic dataset.
  https://openrouter.ai/docs/cookbook/evaluate-and-optimize/jev-classification (read
  2026-09-28). Its design guidance: "categories that never overlap go into one choice
  question... Each [tag] gets its own noul question that is answered with a probability
  between 0 and 1. The odds that one tag applies are judged independently of the
  others." Put category *definitions* in the `choice` question's `criteria`, not its
  instruction text; phrase each `noul` as a plain yes/no question about the item — the
  current workflow's `label`/`needs_reply` questions already follow this shape.
- **Vendor-prescribed threshold calibration (exact procedure, not this document's
  invention):** "Label 100 to 200 representative items by hand, and use runBatch to
  classify them in the same order... compute precision and recall for the different
  tags at each of several candidate thresholds. Raising the threshold increases
  precision at the expense of recall. If you can afford to miss a few items that should
  have the tag, set the lowest threshold where you are satisfied with the precision. If
  you can't afford to miss the items, set the highest threshold whose recall you can
  accept." The cookbook's own worked run used a 150-item calibration sample and swept
  thresholds [0.3 .. 0.9]; when a tag's precision stays low at every threshold, the
  cookbook says "fix the question rather than the threshold" (the cookbook's
  `celebrity` tag never exceeded 0.41 precision because its wording overlapped
  `music`/`film_tv` — the same failure mode already documented in this project as the
  original "Newsletter" vs. marketing overlap). For the `choice` answer specifically:
  "no threshold is needed since confidence itself signals which items need human
  review" — group by confidence band (the cookbook used <0.5, 0.5–0.8, ≥0.8) and route
  low-confidence bands to review; in the cookbook's own run, accuracy by band was
  40%/50%/93%, supporting a review cutoff around confidence ≥0.8.
  https://openrouter.ai/docs/cookbook/evaluate-and-optimize/jev-classification (read
  2026-09-28). This is a stronger, numeric method than the workflow's current fixed
  `CONFIDENCE_FLOOR = 0.55` / `NEEDS_REPLY_FLOOR = 0.75`, which per the code comment
  were never calibrated against a labelled sample ("Tune these two floors against your
  own mail before trusting the run").
- **`state` structure:** the classification cookbook itself keeps `state` minimal
  (`{ post }`, raw text only) and does not recommend adding precomputed booleans.
  TypeSafe's general state-design guidance (not this specific cookbook) does recommend
  structuring `state` as a descriptive JSON object with named parts when there is
  related context to include: "State can also be a JSON object or array containing
  related context, examples, and other information that helps the model answer the
  associated questions... Use an object for most requests so each part of the state has
  a descriptive name." https://docs.typesafe.ai/concepts/state (read 2026-09-28). Since
  the header signals in §1 are exactly "related context that helps the model answer,"
  adding them as extra named booleans/strings under `state` (e.g.
  `state.headers.hasOneClickUnsubscribe`, `state.headers.authPass`) is consistent with
  this general guidance, though no TypeSafe page discusses email headers specifically
  — the *specific application* is this document's **[INFERENCE]**.
- **Per-sender caching/memory: not documented by TypeSafe or OpenRouter.** A full check
  of `docs.typesafe.ai`'s page index, all four pattern pages, the state-concept page,
  and multiple cookbook pages found no guidance recommending entity-keyed (e.g.
  per-sender) caching of Jev verdicts. The only caching primitive found, `JsonCache`
  (used in several TypeSafe cookbooks), is documented purely as a dev-reproducibility
  cache for re-running published code samples at zero API cost — a different purpose
  from production sender memoization. **A per-sender verdict cache is this document's
  [INFERENCE], not a vendor recommendation** — though it directly implements the
  cross-vendor product principle from §3, and Jev's own $0.00005/email cost (already
  measured by the user) makes the *savings* from caching modest in dollar terms; the
  real payoff is fewer Needs Review false-escalations from repeat senders, not spend.

## 5. Spam/phishing specifically

- **What Gmail already catches:** Google's own headline safety statistic: "Gmail blocks
  more than 99.9% of spam, phishing attempts, and malware from reaching you."
  https://safety.google/gmail/ (read 2026-09-28), corroborated by the official Google
  blog directly citing and hyperlinking that same page: "Gmail's AI-powered defenses
  stop more than 99.9% of spam, phishing and malware from reaching inboxes and block
  nearly 15 billion unwanted emails every day," and crediting mandatory authentication
  with cutting "the number of unauthenticated messages Gmail users receive... by 75%."
  https://blog.google/products-and-platforms/products/gmail/gmail-security-authentication-spam-protection/
  (published 2023-10-03, read 2026-09-28). Google's Workspace admin docs describe three
  further pillars — attachment scanning, link/image scanning with click-time warnings
  for untrusted domains, and spoofing/authentication checks (visually-similar-domain
  detection, employee-name spoofing, unauthenticated-sender flagging with "a question
  mark next to the sender's name").
  https://knowledge.workspace.google.com/admin/gmail/advanced/advanced-phishing-and-malware-protection
  (read 2026-09-28). **Important caveat documented on that same page:** "Warning banners
  (yellow box) appear only in Gmail web. Third-party apps do not display a warning
  banner" — an n8n workflow reading via the Gmail API will never see this banner
  signal at all, only the underlying `Authentication-Results` header and label state.
- **What reaches the inbox / the workflow's search (`has:nouserlabels`):** by
  construction, this is mail that already survived Gmail's own filter — i.e. the
  0.1% tail, which skews toward the *harder* cases (convincing phishing, novel
  spoofing, first-seen senders) precisely because the easy cases were already removed
  upstream.
- **Should a small decision model be the phishing gate? No** — for the reasons above:
  Gmail's own multi-signal system (attachment analysis, click-time link scanning,
  domain-similarity detection, DMARC/SPF/DKIM) is the primary defense and already runs
  upstream of everything Jev sees; a single `choice`/`noul` call over from/subject/body
  text has none of Gmail's link-fetch-time or attachment-scanning capability. The
  authentication-results-plus-lookalike-domain check (§1, §5) is the correct
  *first-pass deterministic gate*; Jev's role, if any, should be a second-opinion
  escalator ("does this look like it's impersonating a bank/service the recipient
  actually uses?") that *only ever adds* a route to Needs Review, never clears a
  message as safe. This conclusion follows directly from Gmail's own documented
  architecture (deterministic auth/domain checks upstream, behavioral warnings
  web-UI-only) rather than from any vendor statement about Jev's suitability for
  security decisions specifically — **[INFERENCE]** on the "never let Jev auto-clear
  phishing" design conclusion, though the supporting facts about Gmail's own filter and
  about DMARC's lookalike-domain gap are directly sourced.
- **No published numeric false-negative rate** for what fraction of the surviving 0.1%
  is specifically phishing (vs. spam vs. malware) was found in any primary Google
  source.

## 6. Evaluation

- **The OpenRouter Jev-classification cookbook is itself the best available primary
  reference for evaluating this exact shape of classifier**, and its method transfers
  directly: label 100–200 representative items by hand (the cookbook's own worked
  example used 150 for calibration), run the batch once, and compute a **confusion
  matrix** per tag/threshold (`tp`, `fp`, `fn`), deriving `precision = tp/(tp+fp)` and
  `recall = tp/(tp+fn)`. "`precisionRecall` returns `undefined` instead of a score when
  a threshold predicts no positives or when the sample contains no positive examples
  for a tag. In that case you'll want to label more items rather than pick a threshold
  from an undefined score." https://openrouter.ai/docs/cookbook/evaluate-and-optimize/jev-classification
  (read 2026-09-28).
- **Precision on "safe to archive" as the key metric** maps directly onto the
  cookbook's own precision definition and Google's canonical framing: "the proportion
  of all the model's positive classifications that are actually positive... Use when
  it's very important for positive predictions to be accurate," with the explicit
  worked example of a spam classifier: "False positive (FP): A not-spam email
  misclassified as spam. These are the legitimate emails that wind up in the spam
  folder." https://developers.google.com/machine-learning/crash-course/classification/accuracy-precision-recall,
  https://developers.google.com/machine-learning/crash-course/classification/thresholding
  (read 2026-09-28). For this workflow, the equivalent "positive class" is
  "classifier said Promotions/Newsletters/safe-to-archive" and the FP class to
  minimize is "a message that actually needed the recipient's attention got filed away
  as noise" — i.e. optimize precision on the archive-eligible labels specifically, the
  same way the cookbook optimizes precision on each tag, and accept that recall (a few
  promotional emails slipping into Needs Review) is the acceptable cost, matching the
  cookbook's own tradeoff framing.
- **Minimal sample size:** 100–200 hand-labeled items, the cookbook's own number, is a
  reasonable target against the roughly 750-email one-shot run already completed —
  large enough that positive counts per label are unlikely to be zero (the cookbook's
  own failure mode when they are).

## Recommended changes to the n8n workflow, ranked

Costs below use the user's own measured $0.00005/email and 0.4–0.7s latency baseline.

1. **Add a deterministic header pre-filter stage before the Jev call.** Read
   `List-Unsubscribe`/`List-Unsubscribe-Post`, `List-Id`, `Authentication-Results`
   (SPF/DKIM/DMARC results) from the already-fetched raw headers (the workflow's
   `simple:false` fetch exposes raw headers as `$json.headers['<lowercase-name>']`, verified in §1 — no new API call
   needed, only a new parsing step in the existing Code node) and pass derived booleans
   into `state` alongside the existing fields, per TypeSafe's own state-design guidance
   (§4) and RFC 8058/Gmail's bulk-sender page (§1). **Evidence: proven** (RFC text +
   Gmail's own bulk-sender page + TypeSafe's state guidance). **Effect:** cheap,
   parallel-evaluated context that should reduce the "Newsletter vs. marketing" and
   "receipt vs. promo" overlap failures already observed once (the original 18-category
   incident). **Cost:** near zero — same request, a few more `state` fields, no extra
   Jev spend since the existing questions already run.

2. **Add 2–4 extra `noul` questions in the same request** — "bulk/marketing" (backed by
   the header booleans from #1), "from a real human," "transactional about the
   recipient's own account," and "phishing/impersonation risk." **Evidence: proven**
   (TypeSafe's own multi-Noul-per-state pattern and Speculative Fan-Out docs, §4).
   **Effect:** turns "everything unclear or `Other/Uncategorized` goes to Needs Review"
   into a structured decision tree that can auto-file more confidently (fewer of the
   149 Needs Review items should need human eyes) while making the archive rule (below)
   enforceable in code rather than only via the `choice` label. **Cost:** ~free per the
   vendor's own claim that "adding questions barely changes response time" and Jev
   answers are billed on input tokens only (already paid once per email); expect the
   per-email cost to stay within the same order of magnitude as the current
   $0.00005/email baseline.

3. **Calibrate `CONFIDENCE_FLOOR`/`NEEDS_REPLY_FLOOR` (and any new Noul thresholds)
   against a 100–200-item hand-labeled sample using the cookbook's precision/recall
   sweep and confidence-band table**, replacing the current uncalibrated 0.55/0.75
   constants (the code's own comment admits they need tuning). **Evidence: proven**
   (OpenRouter cookbook's exact numeric method, §4/§6). **Effect:** directly targets
   the observed 288-Promotions/149-Needs-Review imbalance by finding the threshold that
   trades recall for precision the way the user actually wants, instead of guessing.
   **Cost:** one-time labeling effort (100–200 emails) plus one calibration batch run
   (~$0.005–0.01 at current per-email cost) — no recurring cost.

4. **Per-sender verdict cache keyed by `from` domain (or full address), e.g. an n8n
   Data Table**, so a sender seen and confidently labeled N times skips the Jev call
   entirely on the (N+1)th message, applying the cached label/route directly — mirroring
   HEY Screener, SaneBox BlackHole, and Shortwave's per-sender auto-apply (§3).
   **Evidence: [INFERENCE]** — the cross-vendor product pattern is proven, but no
   TypeSafe/OpenRouter doc recommends this specifically for Jev, and it is a new piece
   of workflow state to design and maintain (cache invalidation, re-classification if a
   sender's behavior changes). **Effect:** the main lever on the 288-strong Promotions
   backlog and repeat-newsletter noise — most of that volume is very likely a small
   number of distinct senders sending repeatedly. **Cost:** the cache lookup itself is
   near-free; the *savings* in Jev spend are modest in dollar terms (already
   $0.00005/email) but the queue-shrinking effect on Needs Review is the real payoff.

5. **A "first-time sender" route**: only messages from a sender never seen before (no
   cache entry) go through the full Jev call plus stricter defaults (e.g., default to
   Needs Review unless confidently Promotions/Newsletters), while repeat senders use
   the cache from #4. **Evidence: [INFERENCE]**, directly modeled on HEY's Screener
   (§3) but not a Jev-specific vendor recommendation. **Effect:** concentrates human
   review exactly where genuine judgment is needed (new senders) instead of spreading
   it across the whole 750-email run. **Cost:** depends entirely on #4 being built
   first; no additional API cost beyond the existing Jev call for first-time messages.

6. **Stricter, code-enforced archive rule**: never let the `choice`/`confidence`
   auto-file result skip Needs Review when any of — a header-derived
   "no valid one-click-unsubscribe + no DMARC pass" pattern for Security/Banking-labeled
   mail, the new "from a real human" Noul crosses a threshold, or `Authentication-Results`
   shows a hard SPF/DKIM/DMARC fail on a message the `choice` call wants to file under
   Security/Paper Trail — is true. **Evidence: proven for the underlying signals**
   (RFC 8601/7489 alignment semantics, §1) **combined [INFERENCE]** for the specific
   rule composition, which is a project-specific policy choice, not a vendor
   prescription. **Effect:** a safety net under the existing "it never archives or
   deletes, only labels" design — this only affects which label a message gets, it does
   not change the system's no-delete guarantee. **Cost:** pure code-node logic, no new
   Jev spend.

7. **Shrink the Needs Review queue by tightening the label criteria that produce
   "Other/Uncategorized" fallbacks**, using the confidence-band review-cutoff method
   from the cookbook (§4, §6) instead of the current fixed 0.55 floor, and by fixing
   any tag whose calibration run shows persistently low precision (the cookbook's own
   advice: "fix the question rather than the threshold," §4) — the same category of
   fix that already resolved the original Newsletter/Promotions overlap once.
   **Evidence: proven method** (cookbook), **[INFERENCE]** on which specific criteria
   need rewording until a labeled sample is actually run. **Effect:** directly targets
   the 149-strong Needs Review backlog. **Cost:** one calibration pass, same as #3.

8. **Point the top noisy senders at Gmail's own "Manage subscriptions" view** as a
   parallel, out-of-band cleanup step (unsubscribe at the source rather than only
   labeling), since Gmail's own blog frames this as ranking senders "by the most
   frequent senders" — i.e. it is already the right tool for exactly the 288-message
   Promotions backlog. **Evidence: proven** (§3, Gmail's own blog/support page).
   **Effect:** reduces future incoming volume, complementary to (not a replacement for)
   the classifier. **Cost:** manual, one-time, outside the n8n workflow entirely.

## 7. Measured on the user's own mail (2026-09-28)

Setup:

- **Sample:** 150 emails drawn deliberately from particular labels, not in proportion to the inbox: 45 Needs Review, 45 binned Promotions, and 60 spread across the other target labels.
- **Answer key:** assigned by three GLM `scout` agents from sender, subject and the first 1,200 characters of the body, without seeing each email's current label. It is **not a human key**: 26 of the 150 were marked unsure.
- **Jev variants:**
  - **A** is the workflow request exactly as deployed.
  - **B** is A plus header booleans (`List-Unsubscribe`, `List-Unsubscribe-Post`, `List-Id`, SPF/DKIM/DMARC) and four extra `noul` questions (bulk, human, own_account, phishing).
- **Cost:** $0.015 for A and $0.016 for B.

| Choice floor | A auto-filed | A correct | B auto-filed | B correct |
|---|---|---|---|---|
| 0.55 (template) | 124 | 90.3% | 127 | 89.0% |
| 0.7 | 111 | 93.7% | 111 | 95.5% |
| **0.8** | 101 | **99.0%** | 105 | 97.1% |
| 0.9 | 96 | 99.0% | 98 | 99.0% |

- **The floor is the dominant lever.** Going from 0.55 to 0.8 cut misfiles from about 1 in 10 to about 1 in 100. The deployed workflow now uses 0.8.
- **Recommendations 1-2 (header booleans, extra `noul`s) did not move choice accuracy.** A and B picked the same label on 145 of 150. Their only measurable use was rescuing low-confidence items: `bulk >= 0.9 && human < 0.1 && own_account < 0.2` moved 8 of the 45 items below the floor into Promotions/Newsletters, with 0 errors. That n is too small to act on, so the extra questions were not deployed.
- **`List-Unsubscribe` alone is not a junk signal.** 67 of the 150 carried it, and they included 5 Needs Review, 4 Security, 1 Banking and 1 Subscriptions item.
- **Archive rule:** `Promotions` or `Newsletters` at confidence >= 0.8 archived 42 of the 150 with 0 wrong by the key, i.e. 100% precision, but only about 36% recall of what the key called archivable. The workflow implements this behind `AUTO_ARCHIVE = false`: it is gated on a measured threshold and off until a week of labels has been reviewed. This narrows, rather than contradicts, the "never archive directly" rule below.
- **Phishing:** no item scored `phishing > 0.5`.
- **Re-sorting the existing Needs Review label at 0.8:** 74 of its 139 emails moved to a specific label and 65 stayed.

Deployment findings on the homelab n8n (container capped at 768 MiB):

- **Memory:** multi-round runs over full email bodies (`simple:false` returns `text`, `html` and `textAsHtml`) crashed the container twice. The fix is one round of 50 per run on a 10-minute schedule.
- **Concurrency limits:** overlapping runs, or 50 parallel `messages.modify` calls, return Gmail 429 "Too many concurrent requests for user". The fix is HTTP batching (5 per second) plus node retries.
- **Fetch errors:** mid-loop Gmail fetches intermittently failed with "connection closed unexpectedly". Gmail nodes now retry 3 times, 5 s apart.

## What not to do

- **Never let the model delete, or archive without a measured threshold.** The workflow's existing design —
  labels only, never a destructive action — is correct and should not change; all
  recommendations above only change *which label* a message gets, consistent with
  Gmail's own model of `CATEGORY_*`/`IMPORTANT` as adaptive *hints*, not authoritative
  dispositions (§2).
- **Never trust `IMPORTANT` (or any single Gmail category label) alone as a final
  decision.** Google's own documentation frames it as a behaviorally-learned, per-user,
  correctable prediction with an explicit opt-out — treat it exactly as the existing
  prompt already does, as "weak supporting evidence only" (§2), not as a verified
  ground truth.
- **Never let a probabilistic decision model be the last phishing gate.** Gmail's own
  multi-signal defense (attachment scanning, click-time link checks, domain-similarity
  detection, mandatory authentication) already runs upstream and blocks >99.9% of this
  traffic (§5); anything that survives to `has:nouserlabels` is disproportionately the
  hard tail. A `noul` phishing-risk question should only ever add a route to Needs
  Review, never clear a message as safe.
- **Never trust `Authentication-Results` from anywhere except the header Gmail's own
  receiving MTA stamped.** RFC 8601 itself warns the header's presence proves nothing
  without an assessed trust relationship to the stamping MTA (§1) — safe here because
  it is read via the Gmail API from Gmail's own infrastructure, but this would not
  generalize to an arbitrarily-forwarded message.
- **Never treat DMARC pass as proof against lookalike/cousin domains.** RFC 7489 states
  this limitation explicitly (§1, §5) — a separate lookalike-domain check is needed for
  that threat class; DMARC alignment alone is not it.

## Gaps

- No primary Google source publishes a numeric false-positive/false-negative rate for
  Gmail's spam filter, nor a single explicit primary-source sentence cautioning against
  relying on `IMPORTANT` alone — both are conclusions drawn from the qualitative
  language and opt-out affordance Google does document, not direct quotes.
- No TypeSafe or OpenRouter documentation addresses per-sender caching/memoization of
  Jev verdicts specifically, nor does either address email header signals specifically
  — both applications in this note (recommendations 1 and 4) are this document's
  **[INFERENCE]**, built from the cross-vendor product pattern in §3 and TypeSafe's
  general (non-email) state-design guidance.
- Superhuman's deeper "Structure Your Inbox" and "Custom Split Inbox" help articles
  returned HTTP 403 during research and could not be quoted directly; only the Default
  Split Inbox article was retrieved.
- SaneBox's exact algorithm for weighting crowdsourced BlackHole signals across users
  is not published; only the existence of a suggestion UI and one aggregate usage
  statistic ("2.8 million senders" in 2025) were found.
- No published numeric breakdown of what fraction of Gmail's surviving 0.1% is
  specifically phishing (as opposed to spam or malware) was found in any primary
  source.
