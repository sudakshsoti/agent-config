Agent sandbox guide

A plain-language map of how Pi and OMP will work inside one Docker Sandbox per repository, what still needs activation, and how to recover when you need to.

Current activation status

  • Ready and tested: Docker Sandboxes v0.42.1 is installed and logged in. The balanced global network policy is initialized, and SSH forwarding is false.
  • Contract smoke test passed: direct workspace write-through, outside-home containment, persistence, loopback port publication, closed stdin, and zero sandbox MCP servers.
  • Guarded: a hard-link escape was demonstrated; the in-progress launcher checkpoint engine detects external hard links and refuses launch. Pi/OMP catastrophe guards and the immutable config bundle are committed on this feature branch.
  • Not active yet: the baseline dotfiles launcher is committed, but automatic checkpoint addition is uncommitted and not fully integrated or tested. Live shell wrappers have not been applied; no persistent real-project sandbox exists; Pi/OMP sandbox authentication is not complete.

Read this as a setup and lookup guide, not as a claim that the trial is already your daily default. Wherever a command depends on activation, it is labelled after activation.

What this system is

The intended unit is small: one canonical Git repository, strictly under ~/dev, is mounted read-write into its own persistent Docker Sandbox. Pi or OMP runs in that sandbox. The host Mac keeps Chrome, the checkpoint directory, the launcher, and explicit host escape hatches.

The mount is direct, so edits made by the agent appear in the repository on the Mac. The protection comes from limiting what the sandbox can see, refusing unsafe repository shapes, checking external hard links before launch, and making a full repository checkpoint first.

What changes in my workflow

The everyday command can remain familiar after activation, but the launch path becomes explicit and fail-closed. The important difference is not a new project manager; it is a checkpoint, a repository boundary, and no automatic host fallback.

Before activation / after activation
Before After activation
Pi or OMP runs on the host. pi or omp routes to the current repository's sandbox.
Host process has the host filesystem context. The sandbox sees one direct-mounted repository, not all of ~/dev.
Recovery depends on your existing Git and backup habits. A full repository checkpoint is made outside ~/dev before launch.
Browser work uses normal host Chrome directly. Chrome stays on the host; guest servers are published deliberately to 127.0.0.1.
Host authentication and sessions may already be present. Sandbox OAuth and agent state are separate. Nothing is copied wholesale.

First use, after activation

  1. From the canonical ~/dev/agent-config checkout, run agent-prepare. It builds the host-controlled bundle used for bootstrap.
  2. In the standalone/main clone of the project, run agent-doctor. Fix any failed prerequisite before continuing.
  3. Run pi or omp. The launcher verifies the repository, audits links, creates the checkpoint, creates the sandbox if needed, and installs pinned guest tooling and the committed configuration bundle.
  4. Complete the model login inside that sandbox if the chosen authentication path is supported. This is not complete in the current rollout.
  5. Start a guest development server only when needed, then publish its port with agent-port and open the loopback URL in normal Chrome.

Later use

  1. cd into the same standalone repository clone.
  2. Run pi or omp; the sandbox persists, but a new checkpoint is still made before the launch path proceeds.
  3. Use agent-status to inspect the sandbox and published ports. Stop or unpublish deliberately when finished.

Current rollout boundary. Shell wrappers are not applied, so these sequences are documentation for the activated state, not an instruction to assume the current shell already routes them. Until activation and authentication are completed, use the existing host workflow deliberately.

pi-host and omp-host intentionally run on the host. They are explicit bypasses, not an automatic fallback if sandbox setup fails. If you use one, know which filesystem and credentials that process can reach.

Web development and the browser

A guest development server should bind to 0.0.0.0 inside the VM. The host does not see it until you deliberately publish a port:

Publish a guest server · after activation 

agent-port 3000
# or, host 8080 to guest 3000
agent-port 8080:3000

Open http://127.0.0.1:3000 (or the host port you selected) in ordinary host Chrome. The mapping is loopback-only TCP4. Remove it with agent-unport when finished. Nothing in the repository should publish a port automatically.

Browser boundary. Normal Chrome is the human test browser. Never relay the personal browser, profile, cookies, or 1Password extension into the sandbox. In-VM Playwright Chromium is a later evaluation, not active functionality in this rollout.

Credentials, OAuth, and 1Password

Authentication is its own boundary. A token obtained inside a persistent repository sandbox persists there and is visible to processes that can read the sandbox's agent state while it is active. Treat that sandbox as a separate login boundary.

  • Do not copy host Pi or OMP auth directories into the guest, and do not import the personal browser profile.
  • If local OAuth is chosen, expect one login per persistent repository sandbox. The current Pi/OMP sandbox authentication has not been completed.
  • Later, use project-scoped sbx and 1Password secret handling with destination-bound references where supported. Keep real values out of argv, shell history, temporary files, repositories, images, and broad global sandbox environment.
  • Do not mount or sign into the personal 1Password vault or use its browser extension. If a service account is ever used, keep it dedicated, read-only, project-scoped, and revocable.
  • SSH agent forwarding remains disabled. The current smoke test found zero sandbox MCP servers; host-side stdio or gateway MCP remains out of bounds.

Isolation is not secrecy. An agent can inspect any plaintext secret deliberately made available to its sandbox or target process, and unrestricted egress can exfiltrate accessible material. The sandbox reduces filesystem/process reach; it is not an exfiltration guarantee.

Checkpoints and recovery

Before a sandbox is created or entered, the checkpoint engine walks the full repository, including .git, ignored files, and untracked files. On the Mac's APFS volume, the copy uses copy-on-write cloning: it is initially space-efficient while retaining a separate directory tree. The default retention is the newest eight valid checkpoints.

Checkpoints live under ~/Library/Application Support/agent-sandbox/checkpoints, outside ~/dev, with private directory and metadata permissions. The engine records the repository root, Git head, file count, byte count, fingerprint, and whether the copy used clone mode. It audits hard links: if a file has more links than are present inside the repository, launch is refused because the link could reach an external inode.

Protects: accidental edits, deletion, sandbox removal, and recovery of the repository tree as it existed at a checkpoint, including local ignored and untracked state.

Does not protect: disk failure, theft, corruption of the same disk or volume, or data changed after a checkpoint that was never followed by another one. The owner has no Time Machine and does not plan to use it; same-disk checkpoints are therefore not off-device backup.

List checkpoints · after activation

cd ~/dev/my-project
agent-checkpoints

Recover into a new sibling directory

Recovery is a manual copy from a chosen checkpoint's repository/ directory into a new sibling directory. Do not overwrite the live repository in place. Review the recovered tree, compare Git state, and decide what to bring back with ordinary Git or file operations.

  1. Run agent-checkpoints and choose the checkpoint by timestamp and Git head.
  2. Copy its repository/ directory to a new sibling outside the checkpoint directory, such as ~/dev/my-project-recovered.
  3. Inspect status, ignored files, and local configuration before using it. Keep the original repository untouched until the recovery is understood.

Limitations to keep in view

Accepted limits and current gaps
Boundary What it means
Same-disk only APFS copy-on-write checkpoints do not cover disk failure, theft, or corruption.
Repository is writable Direct mode lets the agent modify the mounted repository; review changes and use checkpoints.
Worktrees refused The launcher requires a standalone/main clone whose Git common directory stays inside that repository.
Only under ~/dev Repositories outside that root, and ~/dev itself, are refused. Never mount all of ~/dev.
First launch slower It may download pinned guest Pi/OMP binaries and install the committed bundle.
Separate state/auth Each persistent repository sandbox has its own sessions, caches, and any local OAuth state.
Unrestricted egress Network reach is not an exfiltration barrier; do not promise narrow egress until it is configured and verified.
Host-code trap Files or hooks modified through the mount can later execute with host permissions if you run them on the host.
Wrapper bypasses Direct binary paths, command pi, or scripts can bypass shell wrappers; wrappers are adherence, not a security boundary.
Early-access sbx Docker Sandboxes and custom secret/kit interfaces may change; rerun the contract suite before upgrades.
No host MCP Sandboxed Pi/OMP must not reach host stdio MCP or a host gateway.
No broad mount The trial uses one repository per sandbox, not a shared agent-dev sandbox over all projects.

Troubleshooting and rollback

Messages to recognise
Message or symptom Action
repository is outside ... ~/dev Change into a canonical standalone repository strictly under ~/dev. Do not work around this by broadening the mount.
Git worktrees are not supported Use the standalone/main clone. The current direct launcher does not support a linked worktree.
checkpoint failed; refusing to start Do not use a host bypass automatically. Read the checkpoint error, inspect hard links and checkpoint storage, then retry only after the cause is understood.
Checkpoint base is on a different filesystem Put the checkpoint base on the same APFS volume as the repository; the engine deliberately refuses a silent full-copy fallback.
bundle is missing; run agent-sandbox prepare From canonical ~/dev/agent-config, run agent-prepare after the bundle paths are committed and clean. Cleanup commands such as status, stop, and reset do not require the bundle.
Doctor reports SSH, MCP, policy, or login failure Fix the reported Docker Sandboxes prerequisite. SSH forwarding must be false; MCP count must be zero for this trial; network policy must report initialized rules.
Browser cannot connect Confirm the guest server binds 0.0.0.0, publish with agent-port, use 127.0.0.1 in Chrome, and check agent-status for collisions or mappings.
OAuth is missing in the sandbox Log in inside that sandbox through the verified future flow. Do not copy a host auth directory or personal browser state.

Remove the trial without a broad reset

  1. Disable only the shell shims in the dotfiles source; do not silently redirect them to host execution.
  2. Apply only the relevant dotfiles targets, refresh shell command hashing, and verify type -a pi omp ompgo ompcodex.
  3. For a repository sandbox you want gone, run agent-status, review mounts/processes/ports, then run agent-reset and type the exact sandbox name. It removes only that sandbox; it does not delete the mounted host repository or its checkpoints.
  4. Revoke any sandbox-scoped credentials as a separate explicit step. Do not use broad sbx reset as a shortcut.

Automatic checkpoint status. The checkpoint addition is currently uncommitted and not fully integrated or tested. Do not treat the design described here as active until that work is reviewed, committed, applied, and its tests pass.

Glossary

Host
The owner’s Mac and its normal filesystem, Chrome, launcher, and explicit host commands.
Sandbox / VM
The Docker-managed isolated environment where Pi or OMP runs for one repository.
Direct mount
A read-write view of the selected host repository inside the sandbox; edits write through to the host repository.
Checkpoint
A full repository copy, including local Git and ignored/untracked state, stored outside ~/dev for recovery.
Loopback port
A host publication bound to 127.0.0.1, allowing host Chrome to reach a guest server without publishing it to the network.
OAuth
A login flow that issues a token; in this design its persisted token belongs to the sandbox where the login occurred.
MCP
Model Context Protocol tooling. This trial allows no host-side MCP servers in the sandbox path.
