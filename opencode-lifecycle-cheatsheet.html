Feature lifecycle

Use ceremony in proportion to risk

Not every idea needs architecture and not every change needs a plan. Escalate only when uncertainty, blast radius, or irreversibility increases.

Phase 01 · Frame

Clarify the outcome

Define the user problem, desired behaviour, constraints, and success signal before asking the codebase for answers.

Normal conversation

Stay with Build for product framing. These lanes are engineering tools, not substitutes for user research, product strategy, or prioritisation.

Phase 02 · Discover

Map the existing system

Find entry points, established patterns, data flow, ownership boundaries, tests, and likely impact.

/locate <question>

Use when repository uncertainty is high. Skip it when Build already has the relevant files and context.

Phase 03 · Define

Turn the goal into steps

Specify exact files, symbols, implementation order, verification, compatibility concerns, and stopping conditions.

/plan <goal>

Use for multi-file work or an unclear path. Skip it for obvious fixes that Build can complete and verify directly.

Phase 04 · Decide

Resolve consequential design

Choose system boundaries, schemas, contracts, migration strategy, security posture, or rollback design.

/architect <decision>

Use only when alternatives have meaningfully different long-term costs. It is read-only and should return a build-ready decision.

Phase 05 · Build

Implement and verify

Make the smallest correct change, run appropriate tests, inspect the diff, and resolve failures.

Default Build agent

Ask directly when you want code changed. Build is the only everyday lane with broad editing and shell access.

Phase 05b · Automate

Execute a prepared checklist

Delegate each item to a fresh worker, verify it, commit it, check it off, and continue without approval pauses.

/execute-plan path/to/PLAN.md

Use only with a clean, explicit markdown checklist and when one commit per item is desirable. It is not an improvised planning command.

Phase 06 · Challenge

Seek independent failure modes

Look for concrete bugs, regressions, security problems, data loss, and missing tests after implementation is stable.

/review [scope]

Use after substantial work, not every typo. DeepSeek provides a different model family and cannot edit the result it judges.

Phase 07 · Release

Ship deliberately

Confirm verification, review findings, migration readiness, observability, and rollback before changing remote systems.

Build + your approval

git push, PR merge, deployment, SSH, SCP, rsync, Terraform apply, and Kubernetes apply require explicit approval.

Phase 08 · Continue

Preserve decisions and state

Capture what changed, why, what was verified, what remains uncertain, and the exact next action.

/handoff [focus]

Use before a break, context switch, or new session. It returns text and does not create files.

Command reference

What each command is for

Every slash command runs as a child session. The main conversation receives the result without absorbing the full reading and reasoning trail.

/locate

Repository reconnaissance. Returns files, symbols, dependencies, and call chains.

  • Use before editing unfamiliar code.
  • Use for impact and ownership questions.
  • Do not ask it to implement.

/plan

Implementation planning for a reasonably understood goal. Produces an executable checklist.

  • Use for multi-file or ordered work.
  • Use when verification needs thought.
  • Do not use for a one-line fix.

/architect

Technical decision-making with Sol at maximum reasoning. Read-only and deliberately rare.

  • Use for contracts, schemas, and migrations.
  • Use when reversal would be expensive.
  • Do not use for ordinary component choices.

/execute-plan

Autonomous checklist execution with fresh workers, evidence, and one commit per item.

  • Use only with a markdown checklist.
  • Expect uninterrupted execution.
  • Do not use if item commits are unwanted.

/review

Independent, read-only review using DeepSeek V4 Flash 0731 through OpenRouter.

  • Use after substantial implementation.
  • Use before risky release or migration.
  • Do not use as a substitute for tests.

/handoff

Compact session continuity: objective, decisions, changes, verification, blockers, next steps.

  • Use before switching context.
  • Use at the end of unfinished work.
  • Returns text; it does not write a file.

Operating discipline

Know where the boundaries are

Permissions protect the obvious boundaries. Good task framing still determines whether the output is useful.

Do this

  • Give `/locate` a precise question, not an entire feature brief.
  • Give `/plan` the intended behaviour and non-negotiable constraints.
  • Use `/architect` before the plan when the design itself is unresolved.
  • Run `/review` after tests pass and the implementation has stabilised.
  • Use `/execute-plan` from a clean worktree with explicit checklist scope.

Avoid this

  • Do not stack every command onto a trivial change.
  • Do not ask Architect to implement what it recommends.
  • Do not treat Review as proof that code works.
  • Do not run Execute Plan on vague prose or when per-item commits are undesirable.
  • Do not approve push or deployment before checking verification and rollback readiness.

The durable pattern

Read cheaply. Decide carefully. Build directly. Review independently.

  1. If you do not know where, use /locate.
  2. If you do not know how, use /plan.
  3. If you do not know which design, use /architect.
  4. If the path is known, ask Build to implement.
  5. If a checklist is ready, use /execute-plan.
  6. If the change is substantial, use /review.
  7. If you are stopping, use /handoff.
